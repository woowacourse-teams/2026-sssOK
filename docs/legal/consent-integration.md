# 동의 화면·가입 연동 후속 설계

이 문서는 제안이며 현재 API 계약이 아니다. 이번 변경은 문서 페이지까지다. 사용자 요청에 따라 동의 화면 구현은 보류하며 기존 로그인 흐름을 유지한다.

## 현재 동작

소셜 로그인 완료 API는 처음 들어온 소셜 사용자를 즉시 REGISTERED 상태로 만들고 토큰을 발급한다 (`SocialMemberLoginService`). 약관 버전이나 동의 시각을 받거나 저장하는 계약은 현재 코드에서 확인되지 않는다. 프론트 체크박스나 localStorage만으로 서버에 동의가 기록됐다고 간주해서는 안 된다.

## 필요한 흐름

- 동의를 근거로 개인정보를 수집한다면 수집 전 적절한 고지·동의가 필요하다. OAuth 후 화면만 추가하면 충분한지는 별도 검토한다.
- 신규 가입과 기존 로그인을 구분하고, 필요한 동의 확인 전 가입이 완료되지 않도록 서버 계약을 설계한다. OAuth 임시 정보의 목적·기간도 정한다.
- 이용약관과 개인정보 수집·이용 고지를 각각 펼쳐 읽고 개별 체크할 수 있도록 한다. 제공하지 않는 마케팅 기능의 동의를 미리 추가하지 않는다.
- 처리방침 공개와 수집·이용 동의를 구분한다. 동의 목적·항목·기간·거부권과 제한을 짧은 고지문으로 별도 확정한다.
- 서버가 약관별 허용 버전·필수 여부·동의 값을 검증하고 계정별 문서 ID/버전·동의 여부·시각(서버 기준)을 저장한다.
- 기존 회원은 최초 적용 또는 재동의가 필요한 변경 때 확인한다. 단순 고지와 재동의를 구분한다.
- 만 14세 이상 확인, 거부·취소, 실패 후 재시도, OAuth 이탈·새로고침 처리를 정한다.
- 익명 인증·업로드·AI 분석·분석 SDK는 회원 로그인 외에도 발생하므로 로그인 화면만으로 모두 해결되지 않는다.
- 선택 분석 동의를 받는다면 SDK 초기화/전송을 실제로 제어하고 철회 경로를 제공한다. 동작하지 않는 쿠키 배너만 만들지 않는다.

초안 상태에서는 소셜 로그인 버튼을 체크박스로 막거나 ‘동의 완료’ 값을 보내지 않는다. 백엔드 계약 확정 후 별도 이슈에서 연결한다.
