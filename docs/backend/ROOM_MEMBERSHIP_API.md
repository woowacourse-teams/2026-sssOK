# 내 방 목록과 방 참여 API (#598)

`RoomMembershipController`와 `RoomMembershipService`에서 목록·입장·나가기를 처리한다.
영속화는 기존 Spring Data JPA 저장소를 사용한다. 목록은 네이티브 조회 projection, 나가기는 참여 기록 ID를 조건으로 한 JPQL 삭제로 처리한다. 방 전체에 명시적인 잠금을 걸지 않는다.

모든 요청은 `Authorization: Bearer {accessToken}`이 필요하며 회원 ID는 인증 정보에서 가져온다.

## 내 방 목록

`GET /api/v1/members/me/rooms`

Path·Query·Body 파라미터 없음. 응답은 `200`, `{"data":{"rooms":[...]}}`이다.
각 항목은 `roomId`, `code`, `name`, `isHost`, `mediaCount`, `memberCount`, `thumbnailUrl`을 포함한다.

- 만든 방과 참여 중인 방을 중복 없이 반환한다. 삭제된 방과 나간 방은 제외한다.
- 참여 시각 내림차순, 동률이면 참여 기록 ID 내림차순이다. 재참여 시 새 참여 시각을 사용한다.
- 참여 인원에는 방장을 포함한다.
- 미디어 수는 갤러리와 같은 PROCESSING·READY 상태 기준이다. PROCESSING은 원본 업로드 완료 후 썸네일 처리 중인 상태다.
- 썸네일이 준비된 사진(JPEG·PNG·GIF) 중 생성 시각과 ID가 가장 최신인 한 장을 대표 사진으로 사용한다.
- 최신 사진의 썸네일이 처리 중이면 이전에 준비된 사진을 유지하고, 처리가 끝나면 최신 사진으로 교체한다. 준비된 사진이 없으면 thumbnailUrl은 null이며 동영상은 선택하지 않는다.
- 미디어는 실제 삭제되므로 삭제된 항목은 집계와 대표 사진에서 빠진다. 나간 회원이 올린 미디어는 유지한다.
- 방이 없으면 rooms는 빈 배열이다. 방 수와 무관하게 목록 DB 조회는 한 번이다.
- 썸네일 URL은 기존 서명·캐시·만료 정책을 따른다. 만료 시 목록을 다시 조회한다.

## 입장

`POST /api/v1/rooms/{roomId}/members`

요청 본문은 `{"code":"공유 링크로 받은 방 코드","nickname":"방에서 쓸 이름"}`이다. `code`는 필수이고 `nickname`은 선택이다. 닉네임을 생략하면 회원의 기본 이름을 사용한다. 이미 참여 중이면 저장된 방 닉네임을 유지하고, 나간 뒤 다시 참여하면 새 닉네임을 지정할 수 있다.

roomId는 순차 증가하는 숫자라 추측할 수 있다. 그래서 공유 링크·QR로 받은 방 코드가 그 방의 코드와 같을 때만 입장시킨다(#626). 이미 참여 중인 사람의 재입장과 나갔다 다시 들어오는 경우도 같은 규칙을 따른다.

- `code`가 없거나(본문 생략 포함) 형식이 틀리면 400(INVALID_ROOM_CODE)이다.
- 형식은 맞지만 그 방의 코드와 다르면 방이 없을 때와 같은 404(ROOM_NOT_FOUND)이다. 코드 검사를 만료·삭제 검사보다 먼저 해서, 코드를 모르는 사람에게 방의 존재나 만료 여부를 드러내지 않는다.

잘못된 코드로 반복 시도하는 경우의 제한은 지금 두지 않는다. 방 코드는 혼동 문자를 뺀 32자 중 8자리라 경우의 수가 약 1.1조(32^8)다. roomId 하나를 정해 두고 맞히려면 평균 약 5,500억 번을 시도해야 한다. 초당 1,000번씩 보내도 평균 약 17년이 걸린다. 게다가 코드만으로 방을 찾는 `GET /api/v1/rooms/{code}`도 같은 경우의 수를 제한 없이 열어 두고 있어, 입장에만 제한을 둬도 새로 막히는 경로가 없다. 코드 길이를 줄이거나 코드 조회에 제한을 도입할 때 입장도 함께 검토한다.

기존 계약 유지: 첫 참여는 201, 이미 참여 중이면 200. 나간 후 재참여는 새 참여이므로 201이다.
참여 기록 삽입에 성공하면 저장한 값으로 즉시 응답을 구성한다. 중복 삽입은 기존 유일 제약과 ON CONFLICT로 방지한다.
다른 요청이 먼저 입장해 삽입하지 못했다면 기존 참여 기록을 한 번만 다시 조회해 반환한다. 그 사이 나가서 기록이 없으면 재시도하지 않고 409(ROOM_MODIFIED)를 반환한다. 클라이언트는 상태를 다시 확인한 뒤 재요청할 수 있다.
입장과 나가기가 겹치면 입장 성공 응답 이후 나가기가 반영될 수 있으며, 입장 응답이 이후 요청의 상태까지 보장하지는 않는다.

## 나가기

`DELETE /api/v1/rooms/{roomId}/members/me`

Path의 roomId는 정수이며 Query·Body는 없다. 성공은 본문 없는 204이다.

- 본인의 참여 관계만 삭제한다. 반복 요청과 미참여 상태도 204이다.
- 삭제되지 않은 방의 방장은 409(ROOM_HOST_CANNOT_LEAVE)이다. 방 삭제 API를 사용한다.
- 삭제된 방의 남은 참여 관계는 방장도 정리할 수 있다.
- 업로드 예약 당시의 방 닉네임을 미디어에 저장해 나가기·다른 닉네임으로 재참여한 뒤에도 사진별 작성자 이름을 유지한다. 계정 탈퇴 시에는 기존처럼 `탈퇴한 사용자`로 표시한다.
- 방·미디어는 삭제하지 않는다. 다시 입장할 수 있다. 동시에 들어온 입장·나가기는 DB가 실제로 읽고 쓰는 순서에 따라 반영된다. 먼저 조회한 참여 기록이 이미 삭제됐더라도 새 참여 기록을 대신 삭제하지 않는다.
- 커밋 후 삭제한 참여 기록에 속한 SSE 연결을 모두 종료한다. 재참여로 생성한 연결과 다른 회원의 연결은 유지한다.
- 이후 참여자 API와 SSE 재연결은 거부된다. 이미 발급된 스토리지 서명 URL은 자체 만료 시각까지 유효할 수 있다.
- 현재 SSE 구현의 단일 서버 인메모리 전제를 유지한다.

## 오류

| HTTP | 코드 | 상황 |
| -- | -- | -- |
| 400 | INVALID_REQUEST_PARAMETER | roomId 형식 오류 |
| 400 | INVALID_ROOM_CODE | 입장 요청에 방 코드가 없거나 형식이 틀림 |
| 401 | UNAUTHORIZED | 인증 누락 또는 잘못된 인증 |
| 404 | ROOM_NOT_FOUND | 입장·나가기 대상 방이 존재하지 않거나, 입장 요청의 방 코드가 그 방과 다름 |
| 409 | ROOM_MODIFIED | 중복 입장 후 재조회 시 참여 기록이 사라짐 |
| 409 | ROOM_HOST_CANNOT_LEAVE | 삭제되지 않은 방의 방장이 나가기 요청 |
| 410 | ROOM_EXPIRED | 만료·삭제된 방에 입장 요청 |

오류 본문과 메시지는 기존 GlobalExceptionHandler/ErrorCode 규약을 따른다.
OAuth의 `renewal.incoming.auth.AuthMember`와 세션 토큰 검증을 사용한다. 소셜 가입은 기존 회원 ID와 방 활동을 유지하며, 기존 계정으로 로그인해 활동을 통합하면 대상 계정으로 목록·방장 권한을 조회한다. 통합된 익명 계정의 토큰이나 로그아웃한 토큰은 401을 반환한다. 익명 회원도 유효한 토큰으로 이용할 수 있다.

마이그레이션은 OAuth의 V45 다음인 `V46__add_my_rooms_index.sql`을 사용한다.

작성자 닉네임은 `V47__add_media_uploader_nickname.sql`에서 저장 컬럼을 추가한다. 기존 미디어는 현재 확인 가능한 방 닉네임 또는 계정 기본 이름으로 보완하며, 이미 사라진 과거 닉네임은 복원하지 못한다.
