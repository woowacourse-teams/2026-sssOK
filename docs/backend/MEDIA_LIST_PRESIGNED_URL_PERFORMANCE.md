# 전체 목록 API의 CPU 부하와 서명 URL 재사용 개선안

작성일: 2026-10-15 · 상태: **로컬 캐시 구현·회귀 검증 완료 / dev 성능 비교 전**

구현 이슈: [#541 — 열람용 서명 URL 로컬 캐시로 반복 서명 CPU 부하 개선](https://github.com/woowacourse-teams/2026-sssOK/issues/541)

## 핵심 요약

**전체 목록을 조회할 때마다 같은 사진의 서명 URL을 다시 만드는 비용을 줄이려 한다.**

| 질문 | 현재 답 |
|---|---|
| 어떤 문제가 있었나? | 전체 목록 부하가 높아지면서 백엔드 CPU가 포화되고 응답이 느려졌다. |
| 어떤 근거가 있나? | 코드에서 반복 서명을 확인했고, JFR에서도 목록의 URL 생성 경로에 실행 샘플이 집중됐다. |
| 어떻게 개선하나? | 권한·DB 조회는 유지하고, 유효한 열람용 URL만 재사용한다. |
| 무엇을 더 확인해야 하나? | 적용 후 CPU·응답 시간 개선 효과와 만료·권한 처리를 검증해야 한다. |

> **범위:** 실제 사용하는 `GET /api/v1/rooms/{roomId}/media/all`과 공유 열람 URL 생성 경로. 미사용 페이지 API는 개선·추가 시험 대상에서 제외한다.
>
> **주의:** URL 생성 비용에 대한 근거는 확보했다. 마지막 실패 실행이 갑자기 악화된 이유까지 모두 밝혀낸 것은 아니다.

## 1. 배경 — 무엇을 확인하려 했나

갤러리에 여러 사용자가 접속할 때 목록 조회가 얼마나 많은 요청을 처리하는지 확인했다. 느려지는 경우에는 CPU·메모리·DB 중 어떤 자원이 원인인지 좁히는 것이 목적이었다.

전체 계획은 [#517](https://github.com/woowacourse-teams/2026-sssOK/issues/517)이다. 우선 작은 조건인 **방 1개·계정 30개·사진 300장**으로 시작했다. 서비스 전체의 수용 인원이나 사진 1,500장 조건을 검증한 시험은 아니다.

### 시험 조건

| 항목 | 조건 |
|---|---|
| 대상 | dev API · `https://dev-api.ssssok.com` |
| 서버 | 기존 실험 기록상 t4g.small · 2 vCPU · 약 1.8GiB RAM |
| 데이터 | 방 1개 · 계정 30개 · 생성 PNG 1280×960 사진 300장 |
| 부하 발생기 | Mac에서 실행한 k6 |
| 관측 자료 | k6 결과, Grafana, 마지막 진단 실행의 JFR |
| 비교 앱 / 스크립트 | `875c942d` / `e25b2644` |
| 시드 ID | `20261014T1339Z-7a48` |

### 시험 방식은 두 가지다

| 방식 | 작동 방식 | RPS의 의미 |
|---|---|---|
| **요청률 고정** | 초당 정해진 횟수로 요청을 시작 | 입력 목표 |
| **사용자 30명 고정** | 각자 조회 → 약 1~3초 대기 → 다시 조회 | 실행 결과 |

요청률 고정 시험의 `VUS=30`은 요청을 보낼 가상 사용자의 상한이다. 항상 30명이 동시에 요청한다는 뜻은 아니다.

**평균 RPS가 같아도 요청이 겹치는 정도는 다를 수 있다.** 사용자 고정 시험에서는 서버가 느려지면 다음 요청도 늦어진다.

### 먼저 해결한 문제

| 기존 문제 | 반영한 수정 |
|---|---|
| 예열·본 측정 전환 시 사용자 중첩, 중단 판정 유예 오류 | [PR #539](https://github.com/woowacourse-teams/2026-sssOK/pull/539): 실행 구간과 초기 요청 분산 수정 |
| URL 생성 중 DB 커넥션을 오래 점유 | [PR #540](https://github.com/woowacourse-teams/2026-sssOK/pull/540): DB 조회 이후 커넥션을 반환하고 URL 생성 |

이후 30명 시험은 오류 없이 완료됐다. **DB 커넥션 점유는 줄었지만 URL 생성 작업량은 그대로여서 CPU 부담이 남았다.**

시드 준비 중 발생했던 썸네일 작업 정체는 별도 문제다. 해당 개선은 [썸네일 작업 대기열 문서](THUMBNAIL_JOB_QUEUE.md)에 기록했다.

## 2. 문제 — 어떤 결과가 나왔나

### 정상 완료한 시험

아래는 **본 측정만의 결과**다. 응답 시간은 읽기 쉽게 ms 단위로 반올림했다. 모든 실행의 HTTP·업무 실패율은 0%, 요약상 dropped는 0이었다.

| 시험 | 예열 / 측정 | 실제 RPS | 평균 | p95 | p99 |
|---|---|---:|---:|---:|---:|
| 고정 1RPS | 1분 / 2분 | 1.01 | 276ms | 403ms | 602ms |
| 고정 2RPS — 1차 | 1분 / 2분 | 2.01 | 244ms | 315ms | 347ms |
| 고정 2RPS — 2차 | 1분 / 2분 | 2.00 | 271ms | 464ms | 574ms |
| 고정 4RPS | 1분 / 2분 | 4.00 | 259ms | 322ms | 568ms |
| 고정 6RPS | 1분 / 2분 | 6.01 | 255ms | 320ms | 371ms |
| 고정 8RPS — 짧은 시험 | 1분 / 2분 | 8.01 | 347ms | 896ms | 1,356ms |
| 고정 8RPS — 시간 통일 | 2분 / 3분 | 8.01 | 291ms | 428ms | 704ms |
| **사용자 30명** | **2분 / 3분** | **8.37** | **1,618ms** | **2,358ms** | **3,546ms** |

*p95는 요청의 약 95%가 완료되는 시간의 경계다. 실패율이 0%여도 응답이 충분히 빠르다는 뜻은 아니다.*

### 결과에서 알 수 있는 것

- **1~6RPS:** 짧은 시험에서 평균 약 250ms를 유지했다.
- **고정 8RPS:** 처리에는 성공했지만, 시간 통일 시험의 호스트 CPU 5분 평균은 약 90%까지 상승했다.
- **사용자 30명:** CPU가 포화되고 응답이 크게 느려졌다.
- **시간 차이:** 예열·측정을 동일하게 맞춰도 30명 시험의 긴 지연은 재현되지 않았다. 실행 시간만으로 차이를 설명할 수 없다.

아직 **“서비스 한계는 30명 또는 8RPS”라고 결론 내릴 수 없다.** 반복 횟수가 적고, 실행 시점·CPU 크레딧·백그라운드 작업을 완전히 통제하지 못했다.

### CPU 그래프에서 주의할 점

Host Overview의 CPU는 **최근 5분 평균**이다. 3분짜리 시험에는 유휴 시간이 섞여 낮게 보인다.

```text
3분간 CPU 100% + 2분간 CPU 0%
→ 5분 평균은 약 60%
```

따라서 짧은 시험의 약 58%와 긴 시험의 약 90%를 그대로 비교하지 않는다. 후속 시험은 시간을 통일하고 CPU 1분 구간과 JVM CPU를 함께 본다.

### 마지막 실패 실행은 별도로 해석한다

| 항목 | 결과 |
|---|---|
| 시작 | 2026-10-15 13:30:25 KST |
| 초기 이상 | 약 4초 후 가상 사용자 소진, 약 10초부터 요청 시간 초과 |
| 본 측정 | 요청 209건 · 평균 약 7.97초 · p95 약 10초 |
| 실패율 | HTTP·업무 실패 모두 14.35% |
| 종료 | 13:33:26 · 본 측정 약 62초 만에 자동 중단 |
| JFR 수집 | 13:32:39~13:33:39 · 60초 |

서버에서도 약 10초의 지연이 관찰됐다. JVM CPU는 약 97%까지 올랐고, 작업 대기와 Swap 활동도 증가했다. 반면 커넥션 획득 대기는 수 ms, GC 정지 시간 비율은 약 2%였다.

**지연은 JFR 수집 전에 시작됐다.** 다만 녹화 이후 오버헤드는 고려해야 한다. JFR에는 부하 중 약 47초와 종료 후 약 13초가 포함된다.

이 실행의 급격한 악화 원인은 미확정이다. 정상 시험과 합쳐 평균을 내거나, 전부 URL 생성 탓으로 단정하지 않는다.

> **집계 주의:** 중도 종료 결과의 `phaseRate=1.16`은 예정 시간 180초로 나눈 값이므로 실제 처리율로 사용하지 않는다. 가상 사용자 부족 경고가 있어 dropped 0만으로 목표 입력량 달성을 판단할 수도 없다. 서버 5xx가 0이어도 클라이언트는 10초 시간 초과로 실패할 수 있다.

## 3. 원인 근거 — 코드와 JFR에서 무엇을 봤나

### 요청 한 번에 URL 약 600개를 만든다

현재 목록 조회는 다음 순서로 처리된다.

```text
권한 확인 → 사진·관련 정보 DB 조회 → DB 커넥션 반환
→ 사진마다 썸네일 URL + 표시 URL 생성 → 전체 JSON 응답
```

| 단위 | 서명 호출 수 |
|---|---:|
| 사진 한 장 | 2회 |
| 사진 300장 목록 한 번 | 약 600회 |
| 목록 초당 8회 | 약 4,800회/초 |

썸네일·표시 URL이 모두 생성되는 조건의 계산이다. 같은 사진을 다시 조회해도 URL을 매번 새로 만든다.

서명 과정에는 요청 객체 구성, 인증 방식 선택, 엔드포인트 처리, URL 인코딩·서명·문자열 생성이 포함된다. 파일을 다운로드하지 않아도 CPU를 사용한다. `S3Presigner` 객체 자체는 이미 재사용하고 있다.

### JFR에서 목록의 URL 생성 경로를 확인했다

Java 실행 샘플 **1,469개 중 545개(37.10%)**가 다음 메서드에 집중됐다.

```text
software.amazon.awssdk.core.internal.util.MetricUtils.lambda$reportDuration$0
```

해당 메서드를 포함하는 세 샘플의 호출 경로는 다음과 같다. 썸네일과 표시 URL 경로가 모두 나타났다.

```text
GetMediaListService.list
  → MediaDetailAssembler.toDetails
  → MediaUrlResolver.resolve
  → MediaUrlSource.Derivative.resolve
  → R2FileStorageAdapter.presignGet
  → DefaultS3Presigner.presignGetObject
  → S3AuthSchemeInterceptor.selectAuthScheme / trySelectAuthScheme
  → MetricUtils.reportDuration
```

**즉, 반복 URL 생성은 실제 실행 샘플이 집중된 경로와 연결된다.**

### 사실과 가설을 구분한다

| 확인한 사실 | 아직 확정하지 못한 것 |
|---|---|
| 목록마다 URL을 반복 생성한다. | 암호학적 서명 계산 자체가 가장 비싼가? |
| 부하 중 JVM CPU가 포화됐다. | 마지막 실행이 갑자기 악화된 이유는 무엇인가? |
| JFR에서 목록 URL 생성 경로가 확인됐다. | 캐시 적용으로 CPU·지연이 얼마나 줄어드는가? |

37.1%는 **Java 실행 샘플 비율**이다. 호스트 전체 CPU 비율이나 SDK 메트릭 기능의 낭비 비율이 아니다. 세 스택도 해당 메서드를 조건으로 추출한 사례이므로, SDK 버그나 유일한 원인을 확정하는 근거로 쓰지 않는다.

## 4. 해결책 — 유효한 URL을 재사용한다

### 기존 방식과 변경 후의 차이

기존에는 미디어마다 `MediaUrlSource`가 썸네일·표시 URL을 직접 서명했다. 같은 사진을 다른 사용자가 조회해도 다시 생성했다. Presigner 객체는 재사용하지만, 생성된 URL은 재사용하지 않았다.

| 관점 | 기존 | 개선안 |
|---|---|---|
| 반복 조회 | 매번 서명 | 유효한 URL 재사용 |
| 만료 시각 | 요청마다 새로 계산 | 발급 시 고정, 적중 시 유지 |
| 권한·DB 조회 | 매 요청 수행 | 동일하게 유지 |
| 운영 부담 | 캐시 관리 없음 | 메모리 상한·만료·동시성 관리 추가 |
| 첫 조회 | 서명 비용 발생 | 동일하게 비용 발생 |

### 선택지 1: 어디에 저장할 것인가

| 선택지 | 장점 | 단점·트레이드오프 | 판단 |
|---|---|---|---|
| 요청 내부 재사용 | 단순하고 요청 간 상태 없음 | 다음 요청에서 다시 생성하므로 반복 조회 개선이 제한적 | 이번 문제의 주 해결책으로 부족 |
| **로컬 캐시 — Caffeine** | 네트워크 왕복·추가 인프라 없이 재사용 | 메모리 사용, 재시작 시 초기화, 서버별 중복 서명 | **초기 선택** |
| Redis 공유 캐시 | 여러 서버에서 URL 공유 가능 | 네트워크·운영·장애 대응·분산 동시성 비용 | 서버 간 중복 비용이 커지면 검토 |
| DB 저장 | 여러 서버 공유, 재시작 후 유지 | 임시 URL 때문에 쓰기·갱신 경합 증가 | 우선순위 낮음 |
| 사전 생성·주기 갱신 | 조회 시 생성 대기 감소 가능 | 조회되지 않는 파일도 서명, 갱신 작업 집중 | 인기 데이터에 한정해 추후 검토 |

저장 위치와 생성 시점은 별도 선택이다. 로컬 캐시와 사전 생성을 조합할 수도 있다. Redis를 사용한다면 사진별 개별 네트워크 호출을 피하기 위한 일괄 조회와 동시 갱신 정책까지 필요하다.

### 왜 로컬 캐시를 선택하는가

**확인된 문제는 같은 사진의 반복 서명이다. 서버 간 공유가 필요한 근거는 아직 없다.**

1. 반복 서명을 줄이면서 새로운 네트워크 의존성을 만들지 않는다.
2. 열람 URL 경로에 한정해 도입하고 같은 부하에서 효과를 비교할 수 있다.
3. 캐시가 사라져도 원래 서명 경로로 복구할 수 있어 영속성이 필수가 아니다.
4. URL 생성 비용을 줄이는 대신 메모리와 만료 관리 복잡성을 받아들인다.

여러 서버에서는 서버 수만큼 최초 서명이 중복될 수 있다. 재시작·퇴출·만료 이후의 첫 요청 지연도 남는다. 로컬 캐시가 항상 최선이라는 뜻은 아니며, 서버별 중복 비용이나 캐시 적중률이 실제 문제가 되면 공유 캐시를 재검토한다.

### 선택지 2: 어느 코드에 적용할 것인가

| 적용 위치 | 장점 | 단점·판단 |
|---|---|---|
| 공통 `R2FileStorageAdapter.presignGet()` | 호출부 변경이 적고 모든 경로에 적용 | 다운로드·ZIP·AI용 만료 정책까지 영향 |
| **열람 전용 URL 제공 컴포넌트** | 열람 정책을 한곳에 모으고 범위 제한 | 컴포넌트·연결 코드 추가 필요. **권장** |
| 목록 응답 전체 캐시 | DB 조회·응답 조립까지 절감 가능 | 사용자별 좋아요·삭제·권한·미디어 상태 최신성 관리 복잡 |

열람 전용 컴포넌트에 캐시를 적용하면 URL만 재사용하고 사용자별 정보는 매번 조립할 수 있다. 다운로드·ZIP·AI의 정책은 이번 변경 범위에서 제외한다.

### 선택지 3: 언제, 어떻게 갱신할 것인가

| 방식 | 장점 | 단점·판단 |
|---|---|---|
| 실제 만료까지 재사용 | 재사용 시간 최대화 | 받은 직후 만료되어 이미지 로딩 실패 가능 |
| **만료 전 요청 시 동기 갱신** | 구현·오류 처리 단순, 남은 수명 확보 | 갱신을 만난 요청은 생성 완료 대기. **초기 선택** |
| 만료 전 비동기 갱신 | 기존 유효 URL을 반환하며 새 URL 준비 | 작업 중복·실패·실제 만료 경계 처리가 복잡 |
| 주기적 일괄 갱신 | 갱신 시점 관리 용이 | 불필요한 서명 및 작업 집중 가능 |

초기에는 기존 수명 30분을 유지하고 만료 2분 전부터 요청 시 동기 갱신한다. 이는 제안값이며 프론트의 재조회 시점과 함께 검증한다. 동일 키의 동시 생성·갱신은 하나로 합친다.

사진 수백 장의 갱신 시점이 겹치는 문제는 키별 중복 억제만으로 해결되지 않는다. 만료 구간에서 부하가 집중되면 갱신 시점 분산이나 비동기 갱신을 후속 적용한다. 접근할 때마다 만료를 연장하는 정책은 사용하지 않는다.

### 선택 결과

**크기 제한이 있는 로컬 캐시 + 열람 전용 컴포넌트 + 요청 시 생성 + 만료 전 동기 갱신**으로 시작한다. 첫 조회와 만료 시 비용이 남는다는 점을 수용하고, 반복 조회의 서명 횟수·CPU·지연 감소를 우선 검증한다.

### 변경 원칙

**권한과 데이터는 매번 확인하고, URL과 그 만료 시각만 캐시한다.**

```text
권한 확인 → 최신 미디어·좋아요·폴더 정보 조회
→ 실제 파일 키로 URL 캐시 확인
   ├─ 유효한 값 있음: 기존 URL과 만료 시각 반환
   └─ 없음 / 만료 임박: 새로 서명해서 저장
→ 최신 데이터와 URL을 합쳐 응답
```

첫 조회·캐시 퇴출·만료 갱신에는 서명 비용이 남는다. DB 조회와 JSON 직렬화 비용도 없어지지 않는다.

### 코드 변경 범위

| 위치 | 할 일 |
|---|---|
| [MediaUrlResolver](../../backend/src/main/java/com/sssok/application/media/MediaUrlResolver.java) | 캐시 지원 URL 제공 컴포넌트 사용 |
| [MediaUrlSource](../../backend/src/main/java/com/sssok/application/media/MediaUrlSource.java) | 직접 서명 대신 URL·고정 만료 시각을 함께 받기 |
| 신규 열람 URL 제공 컴포넌트 | 캐시 조회·생성·갱신·중복 생성 방지·지표 담당 |
| 신규 설정 | 사용 여부, 최대 크기, 갱신 여유 시간 |
| 삭제·교체 처리 | 삭제 확정 후 캐시 제거, 파생본 교체 시 새 키 사용 |

[R2FileStorageAdapter](../../backend/src/main/java/com/sssok/infrastructure/storage/R2FileStorageAdapter.java)의 공통 `presignGet` 전체에 캐시를 붙이지 않는다. 다운로드·ZIP·AI용 URL은 첫 변경에서 제외한다.

`MediaUrlResolver`를 공유하는 목록·상세·SSE 응답은 회귀 검증한다. 전체 응답을 캐시하지 않으므로 사용자별 좋아요 정보도 매번 조립한다.

### 캐시 기본 설계

| 항목 | 제안 |
|---|---|
| 저장 위치 | Caffeine 등 인스턴스 내부 캐시 |
| 크기 | 활성 사진 수·URL 길이를 고려한 상한 설정 |
| 키 | 실제 스토리지 키 + Content-Type + Content-Disposition + 서명 수명 |
| 값 | 서명 URL + 발급 시 확정한 `expiresAt` |
| 재시작 | 캐시는 비워지고 필요할 때 다시 생성 |
| 여러 서버 | 서버별 캐시 유지. 일부 중복 서명은 허용 |

미디어 ID만 키로 쓰지 않는다. 썸네일·프리뷰 재생성 시 **실제 파일 키가 바뀌면 새 URL**을 사용해야 한다.

현재 URL에는 사용자별 서명 조건이 없으므로 사용자 ID는 키에 넣지 않는다. 사용자별 조건이 생기면 설계를 재검토한다. 버킷·엔드포인트·자격증명 변경 시에는 캐시를 비우거나 세대를 구분한다.

## 5. 상세 정책 — 만료·권한·동시성

### 만료: 실제 URL 수명을 늘리지 않는다

| 정책 | 초기 제안 |
|---|---|
| URL 수명 | 기존 30분 유지 |
| 서버 갱신 시점 | 만료 2분 전부터 |
| 재사용 조건 | `현재 시각 < expiresAt - 2분` |
| 생성 실패 | 캐시하지 않고 기존 오류 처리 |
| URL이 아직 없음 | null 결과를 장기 캐시하지 않음 |

```text
14:00 발급 → 만료 14:30
14:10 재조회 → 같은 URL, 만료도 14:30
14:28 재조회 → 새 URL 발급, 새 만료 시각 반환
```

**조회할 때 `expiresAt = 현재 시각 + 30분`으로 바꾸면 안 된다.** 실제 URL은 먼저 끊기는데 화면에는 계속 유효하다고 알리는 문제가 생긴다.

만료는 발급 시 고정한다. SDK 만료 정보를 전달하거나 서명 시각과 수명을 일치시켜 저장하고, 캐시 삽입 완료 시각만으로 계산하지 않는다. 캐시 접근 때마다 수명을 연장하지 않으며 반환할 때도 유효성을 확인한다.

현재 [usePhotosQuery](../../frontend/src/entities/media/model/usePhotosQuery.ts)는 썸네일 만료 1분 전에 목록을 재조회한다. 서버가 2분 전에 갱신하면 새 URL을 받을 수 있다. 장시간 열린 상세 화면과 썸네일이 없는 미디어의 표시 URL 갱신도 확인해야 한다.

### 권한: 기존 검사 이후에만 캐시를 사용한다

[RoomMembershipInterceptor](../../backend/src/main/java/com/sssok/presentation/api/common/RoomMembershipInterceptor.java)의 토큰·방 상태·참여 검사를 유지한다. 이후 미디어 소속·상태까지 확인한 데이터에만 캐시를 적용한다.

| 상황 | 처리 |
|---|---|
| 방 탈퇴·권한 상실 | 다음 API 요청을 기존 검사에서 차단 |
| 방 만료·삭제 | 기존 방 상태 검사 유지 |
| 미디어 삭제 | DB 조회에서 제외하고 삭제 확정 후 관련 캐시 제거 |
| 파생본 교체 | 최신 스토리지 키 사용 |
| 동일 키에 객체 덮어쓰기 | 교체 정책에 맞춰 캐시 무효화 검토 |

**캐시를 지워도 이미 전달한 URL이 즉시 무효화되는 것은 아니다.** 이는 기존 서명 URL 방식에도 있는 특성이다. 즉시 권한 회수가 필요하면 짧은 수명이나 별도 권한 확인 전달 구조를 검토해야 한다.

진행 중 요청이 삭제 전 키를 캐시에 다시 넣는 경우에도, 다음 요청의 DB 상태 검사가 삭제된 미디어 반환을 막아야 한다. 실제 객체 삭제 정책과 캐시 제거는 구분한다.

### 동시성: 같은 URL을 한꺼번에 다시 만들지 않는다

- 동일 키의 **검사·생성·저장·갱신을 원자적으로 처리**한다.
- 모든 파일을 막는 전역 잠금 대신 키 단위로 처리한다.
- 여러 URL이 동시에 만료되는 구간도 부하 검증한다.
- 필요하면 실제 URL 수명은 유지하면서 조기 갱신 시점을 분산한다.

서명 URL·토큰은 로그에 남기지 않는다. 사용자별 좋아요나 참여 권한 결과도 URL 캐시에 넣지 않는다.

## 6. 검증 — 무엇이 좋아져야 완료인가

### 기능 검증

| 검증 영역 | 통과 조건 |
|---|---|
| 재사용 | 같은 조건이면 URL·만료 시각 유지, 실제 서명 호출 감소 |
| 만료 | 갱신 경계 전후와 시계 변화에서 만료 임박 URL을 잘못 반환하지 않음 |
| 동시 요청 | 같은 키의 중복 서명 억제 |

| 프론트 연동 | 목록·상세·SSE와 만료 전 재조회 동작 유지 |

### 성능 검증

**비교 조건:** 사진 300장 · 고정 8RPS · 예열 2분 · 본 측정 3분.

1. 서버·데이터·부하 발생기·백그라운드 작업 조건을 기록한다.
2. 캐시가 비어 있는 첫 조회와 채워진 상태를 나눠 측정한다.
3. 가능하면 개선 전후 각각 3회 반복한다.
4. CPU·지연 여유가 확인되면 기존 30명 시험을 재확인한다.
5. 만료 갱신과 캐시 퇴출 후의 부하도 확인한다.

| 확인할 지표 | 기대하는 변화 |
|---|---|
| 실제 서명 호출 수 | 반복 조회에서 감소 |
| 캐시 적중·갱신·퇴출·크기 | 재사용 동작과 메모리 상한 확인 |
| CPU | 같은 부하에서 감소 |
| API 평균·p95·p99 | 유지 또는 개선 |
| 실제 처리량·실패·누락 | 목표 입력량 처리, 실패·누락 없음 |
| 메모리·GC·Swap·DB 대기 | 새로운 병목이나 악화 없음 |

수치 목표와 허용 p95는 시험 전에 합의한다. 캐시 적중률만 높아진 것으로 성공 판정하지 않는다. 지표 라벨에는 미디어 ID·방 ID·URL 같은 고유값을 넣지 않는다.

## 7. #541 구현 결과와 운영 설정

열람 전용 `MediaReadUrlProvider`를 추가하고 `MediaUrlSource`와 연결했다. 다운로드·ZIP·AI용 `FileStoragePort.presignGet()` 호출은 변경하지 않았다. Caffeine 캐시의 실제 URL 만료와 만료 전 갱신 판단을 분리했으며, 유효한 캐시는 잠금 없이 조회하고 생성·갱신 시에만 키별 원자 연산을 사용한다.

### 적용 설정

| 환경변수 | 기본값 | 용도 |
|---|---|---|
| `MEDIA_URL_CACHE_ENABLED` | `true` | 재사용 활성화. `false`이면 매번 서명 |
| `MEDIA_URL_CACHE_MAXIMUM_SIZE` | `10000` | 서버별 URL 항목 수 상한. 사진 수가 아닌 URL 개수 |
| `MEDIA_URL_CACHE_REFRESH_AHEAD` | `2m` | 만료 전에 새로 생성할 여유 시간 |

dev/prod Compose에 환경변수 전달을 추가했다. 값을 바꾼 뒤 앱 컨테이너를 재생성해야 반영된다. 캐시 설정을 끄고 재시작하면 기존 경로로 복귀한다. 최대 크기는 초기값이며 URL 길이와 실제 메모리 사용을 측정해 조정한다. Caffeine 크기 제한은 유지보수 시 적용되므로 동시 삽입 직후의 순간적인 초과는 가능하다.

파일 키·응답 헤더·TTL을 키로 사용하며 URL과 만료 시각을 저장한다. 현재 R2 어댑터의 버킷·엔드포인트·정적 자격증명은 앱 인스턴스 설정이므로 캐시도 인스턴스 범위로 한정한다. 해당 설정을 바꾸면 앱을 재시작해 캐시를 비운다. 향후 동적 자격증명이나 여러 스토리지 설정을 한 인스턴스에서 사용하면 키와 실제 만료 계산을 확장해야 한다.

`ObjectsOrphanedEvent`를 `AFTER_COMMIT`에서 수신해 삭제된 키의 모든 URL 조건을 제거한다. 롤백 때는 제거하지 않는다. 이미 조회 중이던 요청과 삭제가 겹칠 수 있으므로 캐시 제거를 권한 회수의 근거로 사용하지 않으며, 다음 목록 조회의 DB 상태가 기준이다.

### 관측 지표

| Prometheus 지표 | 의미 |
|---|---|
| `media_read_url_generations_total` | 실제 서명 시도 수. 비활성화 경로 포함 |
| `media_read_url_cache_hits_total` | 유효한 URL 재사용 수 |
| `media_read_url_cache_refreshes_total` | 기존 항목이 남아 있는 상태의 만료 임박 갱신 시도 |
| `media_read_url_failures_total` | 서명 생성 실패 수 |
| `media_read_url_cache_evictions_total` | 크기·TTL에 따른 자동 퇴출. 명시적 삭제 제외 |
| `media_read_url_cache_size` | 서버별 캐시 추정 항목 수 |

TTL로 이미 제거된 항목의 재생성은 generations에 포함되고 refreshes에는 포함되지 않는다. 지표에는 URL·방 ID·미디어 ID를 라벨로 넣지 않는다. 이 지표들은 목록 API 자체의 요청 수와 구분한다.

### 검증 범위와 남은 작업

2026-10-15 로컬에서 `cd backend && ./gradlew test --console=plain` 실행 성공. **총 1,453개 중 1,435개 통과, 실패 0개, 건너뜀 18개**다. 건너뛴 항목은 로컬 ffmpeg/ffprobe 실행 조건을 충족하지 못한 기존 `FfmpegVideoFrameExtractorTest`다. 기본 test 태스크에서 제외하는 performance/external 태그는 실행하지 않았다. PostgreSQL Testcontainers·API 인수 테스트를 포함한 회귀 검증 결과이며 dev 서버의 실제 부하테스트 결과는 아니다.


- 캐시 단위 검증: 재사용, 고정 만료 시각, 만료 임박·실제 만료, 키 분리, 동시 최초 생성·갱신, 실패 재시도, 크기 제한·퇴출, 재시작·비활성화.
- 삭제 검증: 실제 트랜잭션 커밋·롤백에 따른 캐시 제거, DB에서 삭제된 미디어가 남은 캐시 때문에 다시 응답되지 않음.
- 기존 열람·업로드·좋아요·SSE·권한·다운로드 테스트를 회귀 검증한다.
- 사진 300장(썸네일·프리뷰 각 1개)의 목록을 8회 조립하는 테스트에서, 캐시가 비어 있는 첫 회를 포함해 서명 호출이 600회임을 확인했다. 기존 방식의 예상 4,800회 대비 87.5% 감소이며, 이는 mock 호출 수 검증이지 실제 CPU/RPS 측정이 아니다.
- 프론트는 썸네일 만료 1분 전 재조회이므로 서버 기본 갱신 여유 2분과 호환된다. 실제 브라우저의 장시간 상세 화면·썸네일 없는 미디어 만료는 dev에서 별도 확인한다.
- dev 배포 후 동일한 8RPS·2분 예열·3분 측정 및 30명 시험을 다시 실행해야 CPU 개선과 다음 부하 단계 진행 여부를 판단할 수 있다.

### 로컬 결과 파일

아래는 `backend/loadtest/results/`에 있는 실행 결과명이다. 결과 파일은 Git 추적에서 제외되므로 다른 팀원의 체크아웃에는 없을 수 있다. 공유 시 별도 안전한 실험 자료 저장소에 보관한다.

| 결과 파일 | 용도 |
|---|---|
| `list-all-1rps-20261015T013945Z-media-list.json` | 1RPS |
| `list-all-1rps-20261015T014523Z-media-list.json` | 이름과 달리 설정은 2RPS |
| `list-all-2rps-20261015T014952Z-media-list.json` | 2RPS 재실행 |
| `list-all-4rps-20261015T015314Z-media-list.json` | 4RPS |
| `list-all-6rps-20261015T022035Z-media-list.json` | 6RPS |
| `list-all-8rps-20261015T022802Z-media-list.json` | 짧은 8RPS |
| `list-all-8rps-w2m-d3m-20261015T023352Z-media-list.json` | 시간 통일 8RPS |
| `list-30-20261015T004540Z-media-list.json` | 30명 |
| `list-all-8rps-jfr-20261015T043024Z-media-list.json` | 마지막 실패 진단 실행 |

JFR `list8-20261015T043236Z.jfr`는 dev 서버에서 수집했으며, 본 문서의 분석은 사용자가 제공한 summary·hot-methods·실행 스택 출력과 모니터링 캡처에 근거한다. 원본 전체의 정량적 스택 분석을 완료한 것은 아니다. 원본에는 초기 환경변수 이벤트가 있어 비밀정보가 포함될 수 있으므로 공개 저장소에 커밋하지 않는다.
