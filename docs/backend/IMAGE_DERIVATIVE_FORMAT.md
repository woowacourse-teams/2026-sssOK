# 파생 이미지 포맷 선정

관련 이슈: #291 (포맷 결정) · #301 (측정 도구) · #302 (워커 구성)

업로드된 원본에서 만드는 파생본(목록 타일 `thumbnail` 400px, 상세 모달 `preview` 1600px)을
어떤 포맷으로 내보낼지 정하기 위한 문서다. JPEG · WebP · AVIF 세 후보를 같은 조건에서 재고,
그 근거를 남긴다.

## 왜 직접 쟀나

포맷 비교 글은 많지만 대부분 자기 샘플·자기 인코더 설정이다. 우리가 쓰는 것은 우리 사진과
우리 워커 구성이라, 남의 숫자로는 "우리 환경에서도 그런가"에 답할 수 없다. 특히 두 가지가
일반론과 갈릴 수 있다.

- 파생본이 400px / 1600px 로 작다. 포맷 간 격차는 해상도에 따라 달라진다.
- 워커 풀이 동시에 돈다. SVT-AV1 은 한 장에 코어를 여러 개 쓰고 libwebp 는 하나만 쓴다.
  한가한 장비에서 한 장씩 재면 이 차이가 드러나지 않는다.

## 측정 도구

`backend/src/test/java/com/sssok/benchmark/` 에 있다. CI 가 매번 사진 수십 장을 인코딩하지
않도록 일반 테스트가 아닌 별도 Gradle 태스크로 뺐다. AVIF 측정에는 `ffmpeg` (libsvtav1 포함)이
PATH 에 있어야 한다.

| 태스크 | 무엇을 재나 |
|---|---|
| `derivativeFormatBenchmark` | 포맷 · 품질 지점별 변환 시간 · 파일 크기 · SSIM |
| `derivativeConcurrencyBenchmark` | 워커 풀 동시 실행 조건의 포맷별 처리량 |
| `ssimValidation` | 자체 SSIM 구현을 ffmpeg `ssim` 필터와 교차 검증 |

```bash
# 1. 품질-크기 곡선
./gradlew derivativeFormatBenchmark -Psamples=<샘플 디렉터리> -Pout=format.csv

# 2. 곡선에서 SSIM 이 맞는 품질 쌍을 골라 동시 처리량 측정
./gradlew derivativeConcurrencyBenchmark -Psamples=<샘플 디렉터리> \
    -Pwebp=<품질> -Pavif=<CRF> -Pout=concurrency.csv

# 3. SSIM 구현 검증 (무손실 PNG 필요)
./gradlew ssimValidation -Psamples=<무손실 PNG 디렉터리> -Pout=ssim.csv
```

## 측정 설계

### 품질 지점을 포맷마다 8개씩 찍는다

JPEG·WebP 는 0~100 품질, AVIF 는 CRF(낮을수록 고품질)라 축이 다르다. 서로 다른 축을 억지로
맞추는 대신 각 포맷에서 쓸 만한 구간을 훑고 SSIM 으로 견준다.

- JPEG / WebP: 50, 60, 65, 70, 75, 80, 85, 90
- AVIF CRF: 20, 24, 28, 32, 36, 40, 44, 48

네 점만 찍고 눈대중으로 "SSIM 0.977 부근끼리" 맞추면, 고른 지점이 우연히 한쪽에 유리했는지
알 수 없다. 곡선을 촘촘히 만들어 **같은 SSIM 에서의 파일 크기를 보간해** 견준다.

### 동시 실행을 따로 잰다

동시성 1(한가한 장비) · 4(`spring.task.execution.pool.core-size`) · 8(max-size 피크)에서
각각 9회 반복해 평균과 표본표준편차를 같이 낸다. 한 번만 재면 그때 백그라운드에서 뭐가
돌았는지에 따라 값이 흔들려, 두 포맷의 차이가 잡음보다 큰지 말할 수 없다.

동시성 측정의 품질 지점은 코드에 박아 두지 않고 `-Pwebp` / `-Pavif` 로 밖에서 준다. 그리고
측정 전에 두 설정의 SSIM 을 재서 결과 CSV 의 `ssimGaussian` 컬럼에 같이 적는다. **화질이
다른 두 설정의 처리량을 견주면 느린 쪽이 포맷 탓인지 화질 탓인지 갈라 볼 수 없기 때문이다.**
결과 파일만 봐도 공정한 비교였는지 판단할 수 있어야 한다.

### AVIF 는 프로세스 비용까지 포함해서 잰다

JVM 에서 쓸 만한 AVIF 인코더가 없어 `ffmpeg` 프로세스를 띄운다. 입력 픽셀은 파이프로 바로
밀어 넣지만, 출력은 임시 파일을 거친다 — AVIF 는 컨테이너 헤더를 나중에 되돌아가 채우는
구조라 ffmpeg 의 avif 먹서가 non-seekable 출력을 거절한다. 이 왕복 비용은 실제로 도입해도
똑같이 치를 비용이므로 측정에서 빼지 않는다.

## SSIM 구현과 검증

포맷 결정이 SSIM 이라는 하나의 수에 기대는데 그 수를 우리가 직접 구현한다. 구현이 맞는지
확인할 길이 없으면 결론을 믿을 수 없다. 그래서 창을 두 종류 계산한다.

- **가우시안 11x11 (σ=1.5)** — Wang et al.(2004) 원 논문 정의. 보고는 이쪽으로 한다.
- **균등 8x8, stride 4** — ffmpeg `ssim` 필터와 같은 방식. 교차 검증용.

검증 가능한 쪽으로 기계를 맞춰 두고, 보고는 표준 쪽으로 한다는 뜻이다.

### 검증 과정에서 찾은 오류 둘

처음 돌렸을 때 최대 오차 0.053 으로 불합격했고, 원인이 두 겹이었다.

| 원인 | 고친 뒤 최대 오차 |
|---|---|
| RGB PNG 를 넣으면 ffmpeg 이 Y/U/V 가 아니라 R·G·B 평면으로 SSIM 을 낸다 → `format=gray` 로 맞춤 | 0.053 → 0.009 |
| ffmpeg 은 8x8 창을 4픽셀씩 겹쳐 옮기는데 우리는 겹치지 않았다 → 블록 경계 열화를 덜 봐 값이 후해짐 | 0.009 → **0.00070** |

두 번째를 고치기 전 수치는 화질을 실제보다 좋게 보고 있었다.

### 검증 결과

Kodak 무손실 24장 × 품질 5지점 = **120쌍, 최대 오차 0.00070** (허용 0.00500) → 합격.

```bash
./gradlew ssimValidation -Psamples=<무손실 PNG 디렉터리>
# 비교 120쌍, 최대 오차 0.00070 (허용 0.00500) → 합격
```

### CI 가 지키는 것

전체 교차 검증은 샘플과 ffmpeg 이 필요해 CI 에서 돌지 않는다. 대신 `SsimTest` 가 기본 성질만
매번 지킨다 — 같은 이미지는 1.0, 훼손이 커지면 점수가 단조 감소, 해상도 불일치·창보다 작은
이미지는 예외. 메모리에서 만든 64x64 로 끝나 CI 비용은 사실상 없다.

## 측정 환경

| 항목 | 값 |
|---|---|
| 기계 | Apple M5, 10코어, 16GB, macOS 26.5.1 |
| JDK | OpenJDK 21.0.10 |
| ffmpeg | 9.0.2 (libsvtav1) |
| 샘플 | Kodak Lossless True Color Image Suite 24장 (768x512 18장 · 512x768 6장) |
| 측정일 | 2026-09-27 |

한계를 먼저 적는다. **Kodak 은 최대 768px 이라 preview 후보인 1600px 지점은 재지 못했다.**
원본보다 크게 늘리지 않는 규칙 때문에 preview 측정은 원본 폭(512 / 768px) 그대로 돌았다.
1600px 에서 포맷 간 격차가 달라질 수 있으므로, 실제 업로드 해상도의 사진이 모이면 다시 잰다.

## 측정 결과

### 같은 SSIM 에서의 파일 크기

품질 지점 8개로 만든 곡선에서 기준 SSIM 에 해당하는 크기를 보간했다. 괄호는 WebP 대비 비율,
`ms` 는 한 장당 인코딩 시간 중앙값이다.

**thumbnail 400px** (24장)

| 기준 SSIM | JPEG | WebP | AVIF |
|---|---|---|---|
| 0.94 | 27.3KB (161%) · 1ms | 17.0KB (100%) · 6ms | 16.0KB (94%) · 33ms |
| 0.95 | 31.1KB (160%) · 1ms | 19.4KB (100%) · 6ms | 18.6KB (96%) · 33ms |
| 0.96 | 35.7KB (159%) · 1ms | 22.5KB (100%) · 7ms | 21.5KB (96%) · 33ms |

**preview 원본 폭 512 · 768px** (24장)

| 기준 SSIM | JPEG | WebP | AVIF |
|---|---|---|---|
| 0.94 | 61.0KB (140%) · 5ms | 43.8KB (100%) · 20ms | 38.4KB (88%) · 45ms |
| 0.95 | 71.2KB (140%) · 5ms | 50.8KB (100%) · 20ms | 45.0KB (89%) · 46ms |
| 0.96 | 84.8KB (142%) · 6ms | 59.8KB (100%) · 21ms | 53.7KB (90%) · 47ms |

보간은 24장의 평균 곡선 위에서 했다. 사진마다 압축 난이도가 달라 개별 샘플 곡선의 SSIM
구간이 어긋나, 24장 전부에서 같은 기준 SSIM 을 잡을 수는 없었다 (기준 0.95 에서 23/24장,
0.96 에서 21/24장이 개별 보간 가능). 결론이 SSIM 창 선택에 기대지 않는지는 두 창으로
따로 보간해 확인했다 — 균등 8x8 창으로 재도 순위가 같고 비율도 거의 같다
(preview 기준 SSIM 0.95 에서 JPEG 135% · AVIF 90%, 가우시안은 140% · 89%).

### 동시 실행 처리량

`derivativeConcurrencyBenchmark`, 24장 × 9회 반복. 두 설정의 화질을 먼저 맞췄다 —
**WebP q85 SSIM 0.9702 / AVIF crf20 SSIM 0.9711, 차이 0.0009.**

| 포맷 | 설정 | SSIM | 동시성 1 | 동시성 4 | 동시성 8 |
|---|---|---|---|---|---|
| WebP | q85 | 0.9702 | 39.0 ± 4.7 장/초 | 120.6 ± 23.4 장/초 | 197.8 ± 9.3 장/초 |
| AVIF | crf20 | 0.9711 | 17.4 ± 2.4 장/초 | 53.4 ± 6.3 장/초 | 54.8 ± 6.7 장/초 |

**AVIF 는 동시성 4 에서 8 로 늘려도 처리량이 늘지 않는다** (53.4 → 54.8, 표준편차 안).
SVT-AV1 이 한 장에 이미 코어를 다 쓰기 때문에, 워커를 늘려도 나눠 쓸 코어가 없다. WebP 는
같은 구간에서 120.6 → 197.8 로 계속 늘어난다. 한 장씩만 쟀다면 2.2배 차이로 보였을 것이
피크 부하에서는 3.6배로 벌어진다.

## 결론

**WebP 를 쓴다.**

- JPEG 은 같은 화질에서 WebP 보다 40~60% 크다. 인코딩이 3~4배 빠르지만, 파생본 한 장을
  20ms 에 만드느냐 6ms 에 만드느냐보다 전송량이 중요하다. 탈락.
- AVIF 는 같은 화질에서 WebP 보다 4~12% 작다. 대신 인코딩이 2.2~2.4배 느리고, 업로드가
  몰리는 피크에서는 처리량이 3.6배까지 벌어진다. 10% 남짓의 전송량을 아끼려고 치르기에는
  비싼 값이다. 게다가 JVM 안에서 끝나지 않고 ffmpeg 프로세스와 임시 파일을 왕복해야 한다.
- WebP 는 `webp-imageio` 로 JVM 안에서 끝나고, 동시성이 올라갈수록 선형에 가깝게 늘어난다.

### 이 결론이 바뀔 조건

- preview 가 1600px 로 커지면 AVIF 의 크기 이점이 더 벌어질 수 있다. 실제 해상도 샘플로 다시 잰다.
- 워커가 인코딩 말고 다른 일로 이미 포화 상태라면 AVIF 의 코어 독점이 덜 불리해진다.
- SVT-AV1 대신 JVM 네이티브로 쓸 만한 AVIF 인코더가 나오면 프로세스 왕복 비용이 사라진다.

### 남은 기록

원래 동시성 측정은 WebP q85 와 AVIF crf28 을 견주고 있었다. 이번에 재 보니 두 설정의 SSIM 은
0.9702 와 0.9542 로 **0.016 벌어져 있었다** — AVIF 쪽이 더 낮은 화질로 덜 일하고 있었다는
뜻이다. 그런 조건에서도 AVIF 가 졌으므로 결론의 방향은 그대로지만, 공정한 비교는 아니었다.
그래서 품질 지점을 코드에서 빼고 `-Pwebp` / `-Pavif` 로 받게 바꾼 뒤, 측정 전에 SSIM 을 재서
결과에 같이 남기도록 했다.

## 다시 잴 때

품질 기준을 바꾸거나 인코더 버전이 올라가면 같은 도구로 다시 재고 이 문서를 갱신한다.
동시성 측정의 품질 지점은 `-Pwebp` / `-Pavif` 로 주므로 코드를 고칠 필요가 없다.
