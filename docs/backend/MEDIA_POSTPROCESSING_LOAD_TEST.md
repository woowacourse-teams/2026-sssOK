# 미디어 후처리 전후 부하테스트

2026-11-17 · dev · 기존 Java → JNI 일반 → JNI 상세 진단

JNI 일반 모드의 평균 created→READY 지연이 20·100·200장 조건에서 각각 30.9%, 35.3%, 42.2% 감소했다. 이번 두 모드의 본 측정 640장은 모두 READY에 도달했고 실패·누락은 없었다. 아래 수치는 각 조건 1회 관측 결과다.

## 배경과 변경 내용

원본 업로드가 끝나도 썸네일·프리뷰 준비가 늦었다. 기존 200장 조건에서 이미지 한 장의 후처리는 평균 2.22초였지만, 큐 대기는 평균 55.71초였다. 워커 4개가 오래 점유되면서 뒤에 들어온 사진의 대기가 누적되는 구조였다.

이번 변경은 워커 수나 서버 크기를 늘리지 않고 **한 장을 처리하는 시간**을 줄이는 데 집중했다.

| 선택 | 이유와 적용 범위 |
| --- | --- |
| JPEG 가공을 Java에서 libvips JNI로 전환 | 디코딩·변환·WebP 인코딩 비용을 줄인다. Java 21을 유지하고, JPEG 외 형식은 기존 Java 경로를 사용한다. |
| 썸네일·프리뷰 PUT을 제한된 실행기에서 병렬 수행 | 두 전송을 순차로 기다리던 시간을 겹친다. 두 결과가 모두 성공해야 완료 처리한다. |
| 일반 모드와 상세 진단 모드 분리 | libvips의 지연 실행 때문에 내부 연산 시간을 단순히 분리할 수 없다. 진단 때만 중간 픽셀을 확정해 decode/resize/encode를 측정한다. |

가공만 측정한 로컬 벤치마크는 R2·DB·큐·SSE를 포함하지 않는다. 따라서 구현 선택 근거와 실제 사용자 대기 개선 근거를 구분하고, 후자는 이 dev 부하테스트로 확인했다. 과거 메모리 개선은 [업로드 메모리 개선](UPLOAD_MEMORY_IMPROVEMENT.md), 계측 경계는 [업로드 트레이싱](UPLOAD_TRACING.md)을 참고한다.

## 지표를 읽는 방법

`원본 PUT → 완료 등록 → 작업 큐 → 원본 GET → 이미지 가공 → 파생본 PUT → 완료 저장·READY 발행 → 클라이언트 수신`

**READY 평균**은 사진 한 장이 created 알림을 받은 뒤 ready 알림을 받을 때까지의 평균 대기다. **p95**는 표본의 약 95%가 이 시간 안에 완료됐다는 뜻이다. 마지막 사진의 대기는 최대값으로 함께 확인한다. 서버 가공 시간과 큐 대기는 원인을 찾기 위한 별도 지표다.

## 8. 결과 해석과 다음 판단

**일반 모드에서 평균 READY 대기는 20·100·200장 모두 줄었다.** 200장에서는 57.19초에서 33.03초로 감소했다. 가공 시간과 두 파생본 전송의 경과시간이 줄면서 워커 점유와 큐 대기가 함께 감소한 관측과 일치한다. 다만 여러 변경을 함께 배포했으므로 개선율을 JNI와 병렬 PUT 각각의 독립 효과로 나누지는 않는다.

200장 가공 평균은 기존 약 1,069ms에서 일반 모드 약 383ms로 줄었다. 반면 원본 GET은 약 497ms에서 약 515ms로, 뚜렷한 감소가 없었다. 상세 진단의 이미지당 인코딩 합계는 약 637ms에서 약 95ms로 줄었지만, 진단용 실행 경로의 수치이므로 일반 모드 내부 비용으로 그대로 대입하지 않는다.

**완료 등록 API까지 빨라진 것은 아니다.** 200장 HTTP 응답은 기존 약 5.35초에서 일반 모드 약 5.98초로 늘었다. 등록 API는 별도의 검증·저장·알림 경계를 가지며, 이번 결과로 전체 업로드 API가 모두 개선됐다고 결론 내리지 않는다.

상세 진단 20장은 일반 모드보다 빨랐고 100·200장은 느렸다. 각 조건 1회이며 재시작·캐시·JIT·GC·R2 응답·CPU 크레딧을 모두 통제하지 않았으므로, 이 차이를 순수 계측 오버헤드나 모드 우열로 해석하지 않는다. 이전 가공 단독 실험의 오버헤드도 이번 서비스 수치와 구분한다.

후속 판단은 다음 순서로 진행한다.

1. 일반 모드의 동일 조건 반복 측정으로 실행 간 분산과 READY 꼬리 지연을 확인한다.
2. 워커 분리·인스턴스 변경은 별도 실험으로 두고 일반 API 영향과 비용을 함께 측정한다.
3. AI 워커 2개·4개, 외부 429, DB 부하와 AI 전체 완료 지연은 #557의 남은 비교 범위로 유지한다. 이번 READY 성공은 AI 분석 완료를 의미하지 않는다.

## 9. 검증, 복구와 근거 보존

- 기준선 320장과 신규 640장 각각의 등록·created·READY 수신·후처리 성공·READY 발행 건수를 대조했다. 신규 6조건 모두 누락·지연 판정·API 실패·dropped iteration이 0이었다.
- 진단 모드의 decode N개, resize 3N개, encode 2N개와 부모 연결 오류 0을 확인했다. 일반 모드는 fused 실행 N개를 확인했다.
- 측정 중 비계획 재시작·OOM은 없었다. 진단 전환과 복구를 위한 앱 재생성 2회는 측정 구간 밖에서 수행했다.
- 종료 후 임시 compose override를 제거하고 일반 모드로 복구했다. 진단 환경변수는 미설정(기본 false), 이미지 엔진은 libvips이며 내부·외부 헬스가 정상이었다.
- 부하 실행기·자원 수집기를 종료했고 이미지·파생본·AI 실행기의 active/queued가 모두 0임을 확인했다.
- 신규 본 측정 640장과 seed 60장의 테스트 미디어·방 정리 API가 성공했다. 정리 결과의 RESERVED 잔존은 0이었다. 기존 정리 기능으로 삭제하지 못하는 신규 테스트 계정 12개는 남아 있다.
