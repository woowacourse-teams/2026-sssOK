제목: [BE] 열람용 서명 URL 로컬 캐시로 반복 서명 CPU 부하 개선

라벨: `refactor`, `backend`, `exp: hard` · 담당자: `Uechann`

상태: [GitHub 이슈 #541 생성 완료](https://github.com/woowacourse-teams/2026-sssOK/issues/541)

## 작업 내용

**전체 목록을 반복 조회할 때 매번 생성하는 열람용 서명 URL을 로컬 캐시로 재사용하여 CPU 부하를 줄인다.** 권한 검사와 최신 미디어 조회는 유지하고, URL 및 고정 만료 시각만 캐시한다.

### 부하테스트 배경과 관측 결과

- 대상: 실제 사용하는 `GET /api/v1/rooms/{roomId}/media/all`
- 조건: dev, 방 1개·계정 30개·사진 300장, 앱 `875c942d`, 스크립트 `e25b2644`
- 아래 수치는 본 측정 결과이며, 정상 완료한 세 실행의 HTTP·업무 실패율은 0%였다.

| 실행 | 예열 / 본 측정 | 실제 RPS | 평균 | p95 | p99 |
|---|---|---:|---:|---:|---:|
| 고정 8RPS | 1분 / 2분 | 8.01 | 347ms | 896ms | 1,356ms |
| 고정 8RPS | 2분 / 3분 | 8.01 | 291ms | 428ms | 704ms |
| 사용자 30명 고정 | 2분 / 3분 | 8.37 | 1,618ms | 2,358ms | 3,546ms |

사용자 고정과 요청률 고정은 부하 발생 방식이 다르므로 평균 RPS만으로 동일한 시험이라고 판단하지 않는다. CPU 대시보드의 평균 구간도 맞춰 비교해야 한다.

### 구현할 흐름

```text
권한 확인 → 최신 미디어 조회 → 열람 URL 제공 컴포넌트
  ├─ 충분한 유효기간이 남은 캐시: URL + 원래 만료 시각 반환
  └─ 없음 / 만료 임박: 키별로 한 번 생성·저장
→ 최신 미디어 정보와 합쳐 응답
```

## 작업 범위

- [ ] Frontend
- [x] Backend

| 위치 | 변경 내용 |
|---|---|
| `MediaUrlResolver` / `MediaUrlSource` | 직접 서명 대신 열람 전용 URL 제공 컴포넌트 사용 |
| 신규 URL 제공 컴포넌트 | 로컬 캐시 조회·생성·갱신·동시 생성 억제 |
| 캐시 설정 | 활성화 여부, 최대 크기, 만료 전 갱신 여유 시간 |
| 삭제·파생본 교체 경로 | 삭제 확정 후 제거, 최신 파일 키 사용 |
| 관측 | 서명 호출 수, 캐시 적중·갱신·퇴출·크기 측정 |

공통 `FileStoragePort.presignGet()` 전체에는 캐시를 적용하지 않는다. 다운로드·ZIP·AI용 URL, 미사용 페이지 API의 추가 시험, 전체 목록 응답 캐시는 제외한다. 공통 열람 경로를 사용하는 목록·상세·업로드 응답·SSE는 회귀 검증한다.

## 리팩터링 사유

### 기존 구조의 반복 비용

`MediaUrlSource`는 미디어마다 썸네일과 표시용 URL을 새로 서명한다. 두 파일이 모두 있는 사진 300장이면 목록 1회당 최대 600회, 8RPS에서는 초당 최대 4,800회 서명 호출이 발생할 수 있다. 실제 횟수는 미디어 상태에 따라 달라진다. Presigner 객체 재사용과 URL 결과 재사용은 별개다.

마지막 진단 실행의 JFR에서 Java 실행 샘플 1,469개 중 545개(37.10%)가 `MetricUtils.lambda$reportDuration$0`에 관측됐고, 추출한 스택에서 아래 경로를 확인했다.

```text
GetMediaListService → MediaDetailAssembler → MediaUrlResolver
→ MediaUrlSource.Derivative → R2FileStorageAdapter.presignGet
→ DefaultS3Presigner → S3AuthSchemeInterceptor → MetricUtils
```

이는 URL 생성 경로의 비용을 줄일 근거다. 37.1%를 호스트 CPU 비율로 해석하거나 암호화 계산·SDK 메트릭 기능만을 원인으로 확정하지 않는다. 마지막 실패 실행의 급격한 악화 원인 전체를 설명한 것도 아니며, 캐시의 개선 효과는 적용 후 측정한다.

### 대안 비교와 선택

| 선택지 | 장점 | 단점 / 보류 이유 |
|---|---|---|
| 요청 내부 재사용 | 단순, 요청 간 상태 없음 | 요청마다 다시 생성하므로 반복 조회 개선 제한 |
| **로컬 Caffeine 캐시** | 네트워크 왕복·추가 인프라 없이 재사용 | 메모리 사용, 재시작 시 초기화, 서버별 중복 서명 |
| Redis 공유 캐시 | 여러 앱 서버에서 공유 가능 | 네트워크·운영·장애 대응·분산 동시성 비용 |
| DB 저장 | 서버 간 공유와 영속성 | 임시 URL 갱신 때문에 DB 쓰기·경합 증가 |
| 사전 생성·주기 갱신 | 첫 조회 지연 감소 가능 | 조회되지 않는 파일도 서명, 갱신 작업 집중 |

**현재 확인한 문제는 같은 사진의 반복 서명이며, 서버 간 공유가 필요한 근거는 아직 없다.** 로컬 캐시로 가장 작은 범위에서 효과를 검증한다. 메모리 상한과 만료 관리를 추가하는 대신 반복 CPU 비용을 줄이며, 다중 서버 중복 비용이 실제로 커질 때 Redis를 재검토한다.

### 만료·권한·동시성 정책

- 키: 실제 스토리지 키 + Content-Type + Content-Disposition + 서명 수명. 버킷·엔드포인트·자격증명 변경 시 분리 또는 초기화한다.
- 값: URL + 발급 시 확정한 `expiresAt`. 캐시 적중 때 만료 시각을 연장하지 않는다.
- 초기안: 기존 URL 수명 30분 유지, 만료 2분 전부터 요청 시 동기 갱신. 수치는 설정으로 관리하고 프론트의 만료 전 재조회와 함께 검증한다.
- 실제 만료는 서명 시각 및 자격증명 유효성에 의해 제한된다. 삽입 완료 시각을 기준으로 유효기간을 과대 계산하지 않는다.
- 같은 키의 최초 생성과 만료 임박 갱신을 원자적으로 처리한다. 서로 다른 파일의 동시 갱신 부하는 별도 만료 시험으로 확인한다.
- 생성 실패와 URL 미준비 상태는 장기 캐시하지 않는다. 최대 크기를 제한하며 만료한 URL을 반환하지 않는다.
- 기존 방·참여 권한 검사와 DB 상태 조회를 유지한다. 사용자별 좋아요를 포함한 전체 응답은 캐시하지 않는다.
- 삭제 후 캐시 제거는 이미 전달한 URL의 즉시 폐기를 의미하지 않는다. 즉시 권한 회수가 필요한 경우 별도 전달 구조가 필요하다.
- 캐시를 비활성화하면 기존 서명 경로로 복귀할 수 있도록 한다.

## 완료 조건 (Acceptance Criteria)

- [ ] 같은 파일·서명 조건의 반복 조회에서 URL과 원래 만료 시각을 재사용한다.
- [ ] 파일 키·응답 헤더·수명이 다르면 캐시가 분리된다.
- [ ] 최초 요청과 만료 임박 동시 요청에서 같은 키의 중복 생성을 억제하는 테스트가 통과한다.
- [ ] 만료 경계·생성 실패·캐시 퇴출·재시작·비활성화 동작을 검증한다.
- [ ] 권한 상실·방 상태 변경·미디어 삭제·파생본 교체 후 잘못된 데이터가 반환되지 않는다.
- [ ] 목록·상세·업로드 응답·SSE의 URL 계약과 프론트 만료 전 재조회가 유지된다.
- [ ] 캐시 크기가 설정 상한을 지키며 URL·미디어 ID 같은 고유값을 지표 라벨로 기록하지 않는다.
- [ ] 사진 300장·고정 8RPS·예열 2분·본 측정 3분 조건으로 개선 전후 서명 횟수, CPU, 평균·p95·p99, 실패·누락을 비교해 기록한다. 가능하면 각 3회 반복한다.
- [ ] 캐시가 빈 상태·채워진 상태·만료 갱신 상태를 구분해 측정하고 메모리·GC·Swap·DB 대기 악화 여부를 기록한다.
- [ ] 반복 조회의 서명 횟수와 CPU 감소를 확인하고, 사전에 정한 지연 기준과 목표 처리량을 충족한다. 미충족 시 원인을 기록하고 완료 처리하지 않는다.
- [ ] 기존 30명 시험을 재확인하고 다음 부하 단계 진행 여부를 기록한다.
