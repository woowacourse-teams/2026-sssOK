# 썸네일 DB 작업 대기열 — #532

## 확인한 원인과 증거

- 대상: `20261014T1053Z-bb76`, dev 계정 30개·방 1개·생성 PNG 1280×960 300장, AI 검색 분석 활성화.
- 기존 코드: backend 5.0.1, git `11a3e4b5ee4109b0663bfd2cfb2a9f06ddc56051`.
- 마지막 fixtures: 2026-10-14 19:58:05 KST, READY 191 / PROCESSING 109.
- 중앙 Grafana Loki에서 19:53–20:20 KST 범위의 `{environment="dev"} |= "썸네일"`를 조회하고 JSON 119행을 내려받아 mediaId를 대조했다. 조회 제한 1,000행보다 적어 이 쿼리의 잘림은 없었다.
- **최초 제출 거절 로그 109건·고유 mediaId 109개가 fixtures의 PROCESSING 109개와 정확히 일치**한다. READY였던 시드 사진이나 시드 밖 사진의 제출 거절은 이 조회 결과에 없다. 최초 거절은 19:53:40.301, 마지막은 19:53:55.100 KST다.
- 처리 실패 로그 5건은 모두 시드 밖 mediaId `2627`: WebP 인코더가 48-bit RGB `ShortInterleavedRaster`를 받으며 `Incompatible image` 오류를 낸 별도 사례다. 본 이슈에서 인코더를 변경하지 않는다. 새 정책에서는 이런 반복 실패도 최대 시도 횟수 후 FAILED로 수렴한다.
- 회수 배치 로그: 19:55 1건, 20:00 1건, 20:05 50건, 20:10 50건, 20:15 12건. 이 수는 dev 전체이며 배치 로그에는 개별 mediaId가 없어 각 회차의 시드 처리 수는 단정하지 않는다.
- 20:57:36 KST에 기존 시드 인증정보로 목록 GET 3페이지를 읽어 300개 mediaId 모두 READY임을 확인했다. 업로드·AI 분석·추가 부하 실험은 실행하지 않았다. 정확한 마지막 READY 시각은 기존 로그만으로 확인하지 못했다.
- [mediaId별 대조표](evidence/532-thumbnail-rejections.csv): 인증정보, 서명 URL, 원본 로그의 stack trace는 포함하지 않는다.
- 결론: 이 시드의 정체는 제출 거절 후 10분 경과·5분 주기·50개 제한 회수 경로를 기다린 현상이다. AI가 메모리/Swap 압박에 얼마나 기여했는지는 별도 비교 실험이 필요하다.

## 처리 흐름

1. `MediaRegistrar`는 파일 행을 잠근 뒤 PROCESSING 전환과 `thumbnail_job` 삽입을 같은 트랜잭션에서 수행한다. 작업 저장 실패 시 등록도 롤백된다. 최초 작업은 PENDING이다.
2. 디스패처가 로컬 실행 슬롯을 먼저 확보하고, 짧은 DB 트랜잭션에서 실행 가능한 작업 한 건을 `FOR UPDATE SKIP LOCKED`로 선점한다. 서로 다른 인스턴스도 같은 행을 동시에 선점하지 않는다.
3. RUNNING 전환 시 UUID 토큰, 임대 기한, 시도 횟수를 기록한다. DB 커넥션을 반환한 뒤 전용 실행기에 제출한다. 사진·영상 실행기는 고정 크기이며 메모리 대기열 용량은 0이다.
4. 제출 거절은 현재 토큰에 한해 PENDING/RETRY_WAIT로 반환하고 증가한 시도 횟수를 되돌린다. 정상 복귀하면 다음 디스패치 주기에서 다시 제출한다.
5. 원본 다운로드·이미지 변환·파생본 업로드는 DB 트랜잭션 밖에서 수행한다. 실제 업로드 전에 해당 시도의 파생본 키를 DB에 기록한다.
6. 완료 시 파일→작업 순서로 잠그고 토큰과 임대를 확인한다. 미디어 READY와 작업 SUCCEEDED를 같은 트랜잭션에서 기록한다. 영상의 프레임 추출 불가 시 기존처럼 썸네일 없이 READY로 완료한다.
7. 일시 실패는 RETRY_WAIT, 손상 이미지 또는 횟수 소진은 작업·미디어 FAILED, 삭제된 미디어는 CANCELLED다. 명시적인 재업로드 접수는 FAILED 작업을 새 PENDING으로 초기화한다.

`media_id`가 작업 기본키이므로 로그의 mediaId로 작업도 추적한다. `SUCCEEDED / FAILED / CANCELLED`는 작업의 종료 상태다. API의 기존 미디어 상태와 응답 형태는 유지한다. FAILED 미디어가 목록에서 제외되는 기존 정책도 유지하므로, 최종 실패는 작업 DB·로그·메트릭으로 확인한다.

## 학습 포인트와 구현 선택

### 원자성: 접수와 작업 보존 사이의 빈틈 없애기

AFTER_COMMIT 이벤트로만 작업을 실행하면 커밋 직후 프로세스 종료나 실행기 거절 때 실행 요청을 잃을 수 있다. 같은 트랜잭션에 작업을 기록하면 이벤트가 유실되어도 다음 조회가 DB 기록을 찾는다. 이 작업은 영속 작업 테이블을 직접 사용하며 외부 메시지 브로커 발행 단계는 없다.

### 백프레셔: 받을 수 있는 만큼만 실행하기

실행기 큐를 키우면 디코딩된 이미지와 대기 작업이 메모리를 더 사용한다. 여기서는 실행 슬롯을 Semaphore로 제한하고 나머지를 DB에 둔다. 실행기 활성 수를 읽기만 하는 방식과 달리 슬롯 확보 자체가 원자적이다. 슬롯은 실제 워커가 반환할 때 해제한다. 중단 요청에 반응하지 않는 이미지 라이브러리 때문에 슬롯이 계속 차면 경고를 보고 인스턴스를 재시작해야 한다. 새 스레드를 무한히 만들어 우회하지 않는다.

### 선점·임대·heartbeat

행 잠금은 짧은 선점 트랜잭션에서만 사용한다. 긴 이미지 처리 동안 행 잠금이나 DB 커넥션을 유지하지 않는다. 대신 소유권 토큰과 임대 기한을 저장한다. 인스턴스 간 시스템 시각이 동기화되어 있어야 한다. 별도 heartbeat 스레드가 임대를 갱신하며(전용 객체로 감싸 Spring 일반 배치 스케줄러의 자동 설정을 유지), 기본 최대 실행 시간 10분 이후에는 갱신하지 않고 워커에 interrupt를 요청한다. 만료된 임대는 부활시키지 않는다. 장애·재시작 후에는 회수 주기가 만료 RUNNING을 RETRY_WAIT/FAILED로 옮긴다. PENDING은 회수 배치를 기다리지 않는다.

### 늦은 워커의 결과 차단과 멱등성

GC 정지나 네트워크 지연 때문에 임대 만료 후 기존 워커가 살아 돌아올 수 있다. 토큰 비교로 DB의 최종 결과를 보호하고, 토큰이 포함된 파생본 키로 새 오브젝트 덮어쓰기도 막는다. 미채택·실패한 시도의 파생본은 기존 orphan_object 정리 경로에 기록한다. 완료 응답을 잃고 다시 정리하더라도 현재 미디어가 참조하는 키는 제외한다.

이 방식은 장애 경계에서 이미지 연산을 정확히 한 번만 수행하는 보장은 아니다. 재실행을 허용하되 오래된 결과의 반영을 막는다. 복구 때 정리한 키에 오래된 업로드가 다시 완료되고 그 직후 프로세스가 죽는 극단적인 경우에는 미참조 오브젝트가 남을 수 있다. 스토리지와 DB는 하나의 트랜잭션이 아니므로 완전한 오브젝트 누수 방지는 별도 스토리지 대조/보존 정책이 필요하다.

### 지수 백오프와 jitter

총 시도 횟수는 최초 실행을 포함한다. 실패 후 재시도 상한을 5초부터 두 배씩 늘리고 최대 5분으로 제한한다. 실제 대기는 상한의 절반부터 상한까지 임의로 정한다(equal jitter). 장애 복구 직후 모든 작업이 같은 순간 재시도하는 현상을 줄인다. 실행기 제출 거절은 이미지 처리 시도에 포함하지 않지만, 선점 직후 프로세스가 죽은 경우는 한 번의 시도로 계산한다.

## 설정과 관측

`media.thumbnail.queue`의 기본값:

| 설정 | 기본값 | 의미 |
|---|---|---|
| dispatch-interval | 1s | 유휴 워커 시작 간격. 실행 중에는 다음 작업을 즉시 선점 |
| image-workers / video-workers | 4 / 2 | 인스턴스별 동시 실행 수 |
| lease | 2m | heartbeat 유실 후 회수까지의 임대 |
| max-runtime | 10m | heartbeat가 연장할 수 있는 최대 실행 시간 |
| recovery-interval / recovery-batch-size | 10s / 50 | 임대 만료 회수 간격과 상한 |
| max-attempts | 5 | 최초 포함 최대 처리 시도 |
| retry-base / retry-max | 5s / 5m | 백오프 상한의 시작과 최대값 |
| backfill-enabled | false | 기존 PROCESSING 중 작업 없는 항목 보충 |
| backfill-interval | 10s | 보충 배치 간격, 회당 recovery-batch-size |
| metrics-interval | 30s | DB 상태 메트릭 스냅샷 갱신 |

사진 기본값은 dev 비교 결과에 따라 4개로 선택했다. AI 활성·고해상도 사진 조건은 미검증이며 후속 측정한다. 공용 풀은 ZIP·정리·알림에 사용한다. 구 `media.video.worker.*`, `media.thumbnail.stuck-after/sweep-cron/sweep-batch-size`는 제거되었으며 배포 환경변수도 새 설정으로 이전해야 한다.

- `sssok_thumbnail_jobs{state}`: 상태별 작업 수.
- `sssok_thumbnail_wait_oldest_seconds`: 실행 예정 시각을 지난 가장 오래된 대기 시간.
- `sssok_thumbnail_queue_last_refresh_seconds`: 메트릭 조회 성공 시각. 오래되면 상태 스냅샷도 오래된 값이다.
- `sssok_thumbnail_ready_latency_seconds`: 새 작업 등록→READY 지연. 대기·백오프를 포함하며 성공 건만 집계한다. 기존 데이터 보충 건은 보충 시각부터 측정된다.
- `sssok_thumbnail_retried_total / failed_total / recovered_total`: 재시도·최종 실패·임대 회수 횟수.
- 기존 처리 시간과 제출 메트릭의 `source=sweeper`는 재시도 실행을 의미하도록 유지했다. 회수 수 메트릭은 임대 만료 대상 수를 나타낸다.
- mediaId·토큰·attempt는 로그에 기록하며 메트릭 라벨에 넣지 않는다.
- 중앙/개별 Grafana 미디어 전송 대시보드에 사진 전용 실행기와 DB 대기열·지연 패널을 추가했다. 저장소 파일 변경만 했으며 원격 Grafana 설정을 수정하지 않았다.

상태 집계는 30초마다 테이블을 읽는다. 종료 작업을 영구히 쌓을 경우 집계 비용도 증가한다. 운영 규모를 측정한 후 별도 보관·삭제 정책을 정하며, 이 변경은 작업 이력을 자동 삭제하지 않는다.

## 배포 전환·복구

1. 구 버전 워커가 남아 있는 상태에서 신규 대기열 보충을 실행하지 않는다. 업로드를 잠시 제한하고 구 인스턴스의 워커를 배출·중지한다. 구 실행 경로에는 선점 토큰 검사가 없다.
2. V33 마이그레이션을 적용한 새 버전을 기동한다. 이 변경은 새 테이블을 추가하며 기존 미디어 컬럼을 변경하지 않는다.
3. 기존 미완료 미디어가 있으면 `MEDIA_THUMBNAIL_QUEUE_BACKFILL_ENABLED=true`로 보충을 활성화한다. 파일 잠금을 사용하며 이미 있는 작업은 중복 생성하지 않는다. 보충 완료 로그 후 설정을 다시 false로 돌린다.
4. 대기 수 감소, READY 증가, lease 회수·최종 실패 수, DB 커넥션과 메모리/Swap을 함께 확인한다.
5. 롤백 시 신규 워커를 먼저 중지한다. 구 버전 회수 배치는 다시 미디어 PROCESSING을 기준으로 동작한다. 신규 테이블은 즉시 삭제하지 않는다. 다시 새 버전으로 전환할 때 구 워커 배출 후 작업 상태와 미디어 상태를 대조한다.

## 검증과 재측정

로컬 검증은 PostgreSQL Testcontainers의 실제 Flyway/스키마 validate, 동시 선점, 원자적 롤백, 제출 거절 후 복귀, 백오프/한도, heartbeat/최대 실행 시간, 재시작에 해당하는 임대 유실, 오래된 완료/실패 차단, 삭제 경합, 명시적 재업로드, 기존 자료 보충을 포함한다. 실제 PNG 변환과 디스패처를 연결한 테스트에서는 외부 스토리지를 대체하여 입력 종료 후 SUCCEEDED/FAILED로 수렴하는지 확인한다.

공유 dev에서 새 버전의 워커 2개·4개 비교를 각 1회 실행했다(아래 결과). 구 버전과의 통제된 비교 및 AI 활성 실험은 수행하지 않았다. 추가 검증은 다음 절차를 기준으로 한다.

1. 같은 300장 PNG, 30계정/1방, 입력 동시성·속도, AI 설정, 인스턴스/DB 사양, 다른 트래픽 수준을 기록한다. 기존 입력 코드와 이미지 해시를 고정한다.
2. 현재 남은 작업을 정리하고 측정 창을 확보한다. AI 호출 300건에 해당하는 비용 상한을 합의하고 중복 시드는 금지한다. 공유 RDS와 서비스 지표를 먼저 확인한다.
3. 등록→READY p50/p95/p99, 전체 마지막 완료 시간, 최종 실패율, 대기 수와 최대 대기 시간을 기록한다. 실패는 지연 통계에서 빠지므로 반드시 별도로 함께 보고한다.
4. 메모리 가용량, Swap in/out, CPU, DB 연결/CPU/조회시간, API p95와 5xx를 같은 시간축으로 기록한다. 워커 수 변경 실험은 기준 비교 이후 별도 실행한다.
5. 중단 기준 후보: OOM/재시작 1회, 가용 메모리 10% 미만이 30초 지속, Swap in/out이 기준보다 증가한 채 60초 지속, DB 연결 80% 초과가 30초 지속, API 5xx 1% 초과 또는 p95가 기준의 2배를 1분 초과, 합의한 AI 비용 상한 초과. 기존 서비스 SLO가 더 엄격하면 그 기준을 적용한다. 중단 시 새 입력만 멈추고 이미 접수된 작업의 수렴과 복구 상태를 관측한다.
6. 초기 구현 검증 결과를 처리량 개선 수치로 해석하지 않는다. DB 대기열은 거절 후 재처리 공백을 없애며 이미지 인코딩 자체의 속도를 높이지 않는다.
