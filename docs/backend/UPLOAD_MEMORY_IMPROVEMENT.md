# 업로드 후처리 메모리 할당 개선 (#594)

## 문제 상황과 조사 결과

2026-10-24 운영 서버에서 가용 메모리 10% 미만 상태가 5분 지속됐다는 경고가 발생했다.
서버 RAM은 약 1.8GiB, JVM 최대 힙은 1378MiB였다. 당시 고해상도 사진 후처리와
힙 증가·스왑 사용 증가가 시간상 겹쳤다. 컨테이너 재시작이나 커널 OOM 기록은 확인되지 않았다.

18:09와 18:10에 사진 작업이 각각 9개 등록됐다. 두 번째 묶음은 JPEG 3213×5712,
파일당 약 3MiB였다. 썸네일·AI 작업은 약 18:11에 끝났지만 높은 힙 사용량은
18:23 무렵 GC와 함께 감소했다. 작업 종료 이후의 추가 할당 원인은 이번 조사만으로 확정하지 않았다.
따라서 이 변경은 확인된 과다 할당 경로를 개선하며, 운영 경고의 완전한 해결을 입증한 것은 아니다.

## 코드에서 개선한 원인

- 압축 파일이 작아도 원본 전체 디코딩은 큰 픽셀 배열을 만든다. 3213×5712 이미지는
  일반적인 3~4바이트 픽셀 표현에서 약 52.5~70MiB가 필요하다.
- 원본에서 썸네일과 프리뷰를 각각 축소하면서 큰 중간 이미지 버퍼를 반복 할당했다.
- 작은 파생본에도 ZIP용 멀티파트 스트림을 사용해 업로드마다 8MiB 버퍼와 복사 배열을 만들었다.
- 사진 워커 4개가 동시에 실행되므로 각 작업의 메모리 부담이 겹칠 수 있다.

## 적용한 변경과 선택 이유

### 업로드 전략 분리

`R2UploadStrategy` 인터페이스에 `SinglePutUploadStrategy`, `MultipartUploadStrategy`를 구현하고,
`R2UploadStrategyResolver`가 주입받은 전략 중 크기에 맞는 구현을 선택한다.
완성된 파생본은 8MiB 미만이면 PUT, 그 이상이면 멀티파트를 사용한다.
크기를 미리 알 수 없는 ZIP은 기존 스트리밍 API를 유지한다.

작은 파생본의 고정 8MiB 버퍼를 제거하지만 SDK의 요청 본문 복사까지 제거한 것은 아니다.
멀티파트 실패 시 중단하고, 중단 실패가 원래 오류를 가리지 않도록 처리한다.

### 프리뷰 픽셀 재사용

원본에서 프리뷰 크기의 이미지를 만든 뒤, 압축 전 픽셀에서 썸네일을 만든다.
프리뷰를 인코딩했다가 다시 디코딩하지 않으므로 손실 압축을 중복 적용하지 않는다.
프리뷰가 없거나 썸네일보다 작게 설정된 경우에는 별도로 생성한다.

### JPEG 축소 디코딩

`DerivativeImageDecoder`가 헤더에서 원본 치수를 보존하고 JPEG에 source subsampling을 적용한다.
EXIF 방향을 반영한 원본 표시 너비를 썸네일·프리뷰 중 더 큰 목표 너비로 나눈 정수값을
샘플링 간격으로 사용한다(최소 1). 다른 포맷은 기존 해상도로 읽는다.

3213×5712 JPEG에 목표 너비 1600이면 1607×2856으로 디코딩되어 결과 픽셀 수가 약 1/4이 된다.
최종 출력 크기는 샘플링된 치수 대신 원본 표시 치수에서 계산하여 누적 반올림 차이를 막는다.
EXIF 방향은 축소 후 한 번 적용하고, 원본 파일과 기록되는 원본 치수는 보존한다.

서브샘플링은 전체 픽셀을 읽은 뒤 축소하는 방식과 세부 표현이 다르다.
사용자는 비교 화면을 확인하고, 원본을 보존하는 조건에서 썸네일·프리뷰의 차이를 수용했다.
사진 워커 수는 4개로 유지한다.

## 검증 결과

### 화질과 치수

기존 화질 실험실의 실제 JPEG 53장(대부분 3800×5000 전후)을 동일 설정으로 처리했다.
썸네일은 너비 400 / WebP quality 0.80, 프리뷰는 너비 1600 / quality 0.85다.
기존 출력과 비교한 휘도 SSIM(8×8 균등 창)은 최종 썸네일 평균 0.9759,
프리뷰 평균 0.9144였다. 이는 기존 결과와의 유사도이며 절대 화질 점수나 합격 기준이 아니다.
최종 코드의 썸네일·프리뷰 106개는 모두 기존 출력 치수와 일치했다.
개인 사진과 비교 이미지는 저장소에 포함하지 않는다.

### 메모리와 처리 시간

2026-10-25 로컬 macOS / Temurin JDK 21.0.7에서 고해상도 사진 9장과 워커 4개로 측정했다.
각 실행은 새 JVM이며 `-Xms128m -Xmx1378m -XX:+UseG1GC`를 동일하게 적용했다.
동일 9장으로 워밍업 1회 후 본 측정 1회를 수행하고, 방식별로 3회 실행했다.
실행 순서는 A-B-C / C-A-B / B-C-A다. 강제 GC는 호출하지 않았다.

- A: 기존 전체 디코딩·개별 축소·멀티파트 업로드
- B: 전체 디코딩 + PUT·프리뷰 재사용
- C: B + JPEG 축소 디코딩·원본 비율 기준 치수 보정(최종 코드)

| 지표, 3회 중앙값 | A | B | C |
|---|---:|---:|---:|
| 워커 누적 할당량(MiB) | 2406.2 | 1859.8 | 646.8 |
| 관측 최대 힙(MiB) | 1203.1 | 758.9 | 394.1 |
| 관측 최대 RSS(MiB) | 1484.6 | 1266.1 | 721.5 |
| 처리 시간(초) | 3.025 | 3.433 | 1.701 |
| GC 횟수 | 40 | 37 | 15 |
| GC 수집 시간(ms) | 19 | 21 | 11 |

C의 RSS 범위는 697.3~817.6MiB, A는 1384.3~1583.9MiB였다.
이 조건에서 C는 A 대비 누적 할당량 약 73%, RSS 중앙값 약 51%를 줄였다.

### 해석의 한계

- 입력 9장 약 109.4MiB는 미리 읽어 유지했다. 입력 읽기 할당·시간은 측정에서 제외했다.
- 누적 할당량은 워커 스레드의 Java 객체 할당량이며 네이티브 할당량은 포함하지 않는다.
- 힙은 5ms, RSS는 약 50ms 간격의 관측 최대값이다. 순간 피크를 놓칠 수 있다.
- 실제 업로드 버퍼와 SDK 요청 본문을 만들고 끝까지 읽되, R2 통신은 모의 처리했다.
  HTTP 클라이언트, 네트워크 대기·재시도, DB·Spring 서버의 전체 부하는 포함하지 않는다.
- 최대 메모리와 시간은 실행별로 변동한다. 짧은 3회 측정으로 일반적인 운영 성능을 보장하지 않는다.
- 반복 업로드 후 유휴 메모리 유지나 운영 가용 메모리 경고 해소는 아직 검증하지 않았다.

ZIP·영상 경로와 PostgreSQL 작업 큐의 관련 회귀 테스트로 검증한다.
원본 파일·워커 수·JVM 운영 설정은 변경하지 않는다. 백엔드 버전 의도는 patch다.
커밋·PR·배포는 별도 절차로 진행한다.
