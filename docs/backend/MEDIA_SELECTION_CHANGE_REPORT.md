# 미디어 선택 범위 API 변경 및 성능 측정

측정일: 2026-09-21  
관련 이슈: #248

## 변경 효과

기존 `mediaIds` 배열은 클라이언트가 현재 알고 있는 ID만 표현할 수 있었다. 따라서 페이지네이션된 화면에서
전체 선택을 구현하려면 모든 페이지의 ID를 먼저 가져와 요청에 실어야 했다.

새 `selection`은 다음 네 상태를 서버가 방 전체 데이터를 기준으로 해석한다.

| 상태 | 요청 |
|---|---|
| 아무것도 선택하지 않음 | `include` + 빈 `ids` |
| 일부 선택 | `include` + 선택한 `ids` |
| 전체 선택 | `exclude` + 빈 `ids` |
| 전체 선택 후 일부 해제 | `exclude` + 해제한 `ids` |

이에 따라 다음 효과가 생겼다.

- 페이지에 아직 로딩되지 않은 미디어까지 포함하는 정확한 전체 선택이 가능하다.
- 중복 ID는 한 번만 처리하고, 다른 방의 ID는 대상에서 제외한다.
- `exclude`는 방 전체를 조회한 후 Java에서 제외하지 않고 저장소 쿼리의 `NOT IN` 조건으로 처리한다.
- 실제 처리 대상 개수로 삭제 500건, 다운로드 1,000건 제한을 검사할 수 있다.
- 선택 해제된 행은 DB에서 애플리케이션으로 전송하거나 엔티티로 생성하지 않는다.

## API 변경량

선택 UI 기반 다건 API 5개의 요청 필드를 변경했다.

| API | 기존 | 변경 |
|---|---|---|
| `PUT /rooms/{roomId}/media/folders` | `mediaIds` | `selection` |
| `DELETE /rooms/{roomId}/media/folders` | `mediaIds` | `selection` |
| `DELETE /rooms/{roomId}/media` | `mediaIds` | `selection` |
| `POST /rooms/{roomId}/downloads/batch` | `mediaIds` | `selection` |
| `POST /rooms/{roomId}/downloads/zip` | `mediaIds` | `selection` |

`folderId`와 `folderIds` 계약은 유지했다. 업로드 완료 API의 `mediaIds`는 선택 UI가 아니라 실제 업로드 성공
결과를 보고하는 필드이므로 변경하지 않았다.

요청 본문의 정량 변화는 다음과 같다. 공백 없는 UTF-8 JSON 기준이며 예시의 문자는 모두 ASCII다.

| 요청 | 기존 | 변경 | 변화 |
|---|---:|---:|---:|
| ID 3개 선택 | 20 B | 46 B | 26 B 증가 |
| 미디어 10,000개 전체 선택 | 48,908 B | 41 B | 99.92% 감소 |
| 10,000개 전체 선택 후 10개 해제 | 약 48 KB의 포함 ID | 61 B | 제외 개수에 비례 |

일부 선택은 `mode`와 `selection` 래퍼 때문에 요청이 조금 커진다. 반대로 전체 선택은 전체 ID 개수와 무관하게
고정 크기로 표현되며, 일부 해제도 해제한 ID 개수에만 비례한다.

## 성능 측정

### 환경

- Java 21.0.7
- Spring Boot 3.5.8 / Hibernate 6.6.36
- PostgreSQL 16.14 (`postgres:16-alpine`, Testcontainers)
- Docker Desktop 27.5.1, 컨테이너 할당 메모리 약 7.8 GB
- 방 A 미디어 10,000건, 다른 방 미디어 10,000건
- 실제 `stored_file` 전체 컬럼과 `FileRepositoryAdapter`의 엔티티·도메인 변환 경로 사용
- 워밍업 5회, 측정 15회, 실행 순서를 교차하고 중앙값 사용

비교 대상은 다음과 같다.

1. 기존 가상 방식: 방의 미디어 10,000건을 모두 조회하고 Java `Set`으로 제외
2. 변경 방식: `room_id = ? AND id NOT IN (...)`으로 DB에서 제외한 뒤 조회

### 결과

| 제외 ID | 결과 행 | 기존 중앙값 | DB 제외 중앙값 | 응답 시간 변화 | 애플리케이션 매핑 행 감소 |
|---:|---:|---:|---:|---:|---:|
| 0 | 10,000 | 16.709 ms | 15.329 ms | 8.3% 감소 | 0% |
| 10 | 9,990 | 15.171 ms | 15.908 ms | 4.9% 증가 | 0.1% |
| 1,000 | 9,000 | 15.190 ms | 16.978 ms | 11.8% 증가 | 10% |
| 9,000 | 1,000 | 16.145 ms | 13.479 ms | 16.5% 감소 | 90% |

### 해석

이번 변경을 모든 상황에서의 속도 개선이라고 표현할 수는 없다. 제외 ID가 늘면 `NOT IN` 파라미터 구성과 DB 비교
비용도 늘기 때문에, 제외율 10% 측정에서는 기존 방식보다 11.8% 느렸다. 반면 결과 행이 90% 줄어드는 경우에는
네트워크 전송과 엔티티 변환 감소가 조건 비교 비용을 상쇄해 16.5% 빨라졌다.

실제 UI의 대표 사용 패턴인 “전체 선택 후 소수 해제”는 요청 크기를 크게 줄이지만, 서버가 처리해야 할 결과 행은
거의 그대로이므로 서버 응답 시간 개선은 크지 않다. 이 변경의 주된 가치는 다음 순서로 보는 것이 정확하다.

1. 페이지네이션과 무관한 전체 선택의 정확성
2. 전체 선택 요청 크기 감소
3. 제외된 미디어를 애플리케이션 메모리에 올리지 않는 상한 보장
4. 제외율이 높은 요청에서의 처리 시간 단축

이 결과는 로컬 단일 실행의 마이크로벤치마크이며 운영 지연 시간을 보장하지 않는다. 운영에서는 방별 미디어 수,
제외 ID 수, DB·애플리케이션 간 네트워크에 따라 수치가 달라질 수 있다.

## 재현 방법

벤치마크는 일반 테스트 실행에서는 건너뛰며 다음 명령으로 명시적으로 실행한다.

```bash
cd backend
RUN_MEDIA_SELECTION_BENCHMARK=true ./gradlew test \
  --tests 'com.sssok.infrastructure.persistence.file.MediaSelectionQueryPerformanceTest' \
  --rerun-tasks
```

구현은 `MediaSelectionQueryPerformanceTest`에 있으며 데이터 생성, 워밍업, 교차 실행, 중앙값 계산을 포함한다.
