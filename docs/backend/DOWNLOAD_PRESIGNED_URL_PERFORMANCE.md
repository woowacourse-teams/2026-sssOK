## 핵심 요약

| 질문 | 답 |
|---|---|
| 무엇이 문제였나? | 다건 다운로드(`POST /api/v1/rooms/{roomId}/downloads/batch`)가 사진마다 서명 URL 을 만들어, 300장 요청 1건이 서버에서 약 110ms 걸리고 요청 1건/초마다 앱 CPU 가 약 5.5%p 씩 올랐다. dev(2 vCPU) 기준 초당 약 17건에서 CPU 가 찬다. |

| 계약이 바뀌었나? | 아니다. 응답 필드·`expiresAt`(요청 시각 + 5분)·에러는 그대로다. |

## 1. 원인 — 사진마다 하는 일 중 무엇이 비싼가

#581 측정(2026-10-22)에서 300장 다건은 부하와 관계없이 건당 약 110ms 였고 DB 는 원인이 아니었다(요청당 쿼리 3개, 커넥션 대기 0, RDS CPU 5~6%). 이슈 완료 조건대로 구현 전에 사진마다 하는 작업 중 무엇이 비싼지 프로파일로 나눴다.

### 측정 조건 (로컬)

- 앱: develop `a0876bd2` JAR, `local` 프로필에 SQL 출력·debug 로그 끔, 로컬 PostgreSQL(pgvector) + MinIO, 디스코드 웹훅 빈 값
- 시드: 방 1개·사진 300장 (`backend/loadtest/seed/seed.mjs`)
- 부하: k6 `media-download.js` 다건 300장, `BATCH_FETCH=none`, 초당 8건, 예열 30초 후 JFR `ExecutionSample` 1ms 간격으로 85초 기록
- 분류: 요청 스레드(`http-nio-*`) 샘플을 호출 스택의 바깥 프레임부터 보며 처음 맞는 범주로 나눴다 (샘플 3,747개)

### 결과

|---|---:|
| **서명 (`R2FileStorage.presignGet`)** | **79.1%** |
| 톰캣·스프링 등 기타 | 8.1% |
| 응답 직렬화 (Jackson) | 5.5% |

서명 안을 SDK 단계별로 다시 나눴다 (서명 샘플 2,963개 기준).

| `DefaultS3Presigner.presignGetObject` 아래 단계 | 비중 |
|---|---:|
| `PresignedGetObjectRequest` 생성 (결과 URL 재파싱 포함) | 31.5% |
| SRA 서명 파이프라인 (`doSraPresign`: 정규화·인코딩) | 29.3% |
| 초기 인터셉터 실행·실행 컨텍스트 생성 | 27.8% |

- 파일명 처리·직렬화는 합쳐도 8% 안팎이라 줄여도 효과가 작다. 서명 준비 비용을 없애는 것이 가장 크다.
- 서명 1회 비용(노트북, 2만 회 평균, 3회): presigner 28~68µs → 서명기 직접 호출 8~11µs.

## 2. 해결 — presigner 를 거치지 않고 SDK 서명기를 부른다

### 선택지

| 방식 | 장점 | 단점 | 판단 |
|---|---|---|---|
| **SDK 서명기 직접 호출** | 첫 요청부터 모든 요청이 싸진다. URL·`expiresAt` 계약이 그대로다. 서명 계산은 SDK 가 계속 한다 | presigner 가 하던 요청 조립을 직접 해야 한다 → SDK 를 올릴 때 결과가 달라질 수 있다 | **채택.** 동일성 테스트로 위험을 막는다 |
| 서명 URL 캐시 (#541 방식) | 팀 선례가 있다 | 같은 폴더를 다시 받을 때만 효과, 첫 요청의 300번 서명은 그대로. 재사용하면 `expiresAt` 이 항목마다 짧아져 프론트엔드와 계약을 맞춰야 한다. 중복 파일명이 대상 목록에 따라 달라져 적중률도 불확실 | 보류. 직접 호출로 부족할 때 더한다 |
| SigV4 를 직접 구현 | 가장 싸다 | 서명 규칙을 우리가 책임진다 | 제외 |

### 구현 (#672)

- `R2GetObjectSigner` (신규, `renewal/outgoing/storage`)
  - path-style GET 요청(`/버킷/키`, 키는 `SdkHttpUtils.urlEncodeIgnoreSlashes`)을 직접 조립하고 `response-content-disposition`·`response-content-type` 을 쿼리에 넣는다 (값이 없으면 뺀다 — presigner 와 같다).
  - `AwsV4HttpSigner` 에 presigner 가 R2 설정에서 쓰던 값을 그대로 준다: 서비스 `s3`, 리전 `auto`, 서명 위치 쿼리, 유효기간 `ttl`, 본문 미서명(UNSIGNED-PAYLOAD), 경로 정규화·이중 인코딩 끔.
  - 서명기는 상태가 없어 하나만 만들어 쓴다. 시계를 주입받아 테스트에서 서명 시각을 고정한다.
- `R2FileStorage.presignGet` 이 이 서명기를 쓴다. 기존 presigner·client 처럼 처음 쓸 때 만들어, 자격증명이 없는 환경에서도 스프링 컨텍스트가 뜬다(`R2FileStorageLazyInitTest`). `presignPut`(업로드)은 그대로 presigner 를 쓴다.
- `FileStorage` 포트와 그 위 서비스(`DownloadUrlIssuer`·다건·단건·ZIP)는 바꾸지 않았다. 따라서 `presignGet` 을 쓰는 다른 경로(ZIP 상태 조회, 열람 URL 캐시 미스, 썸네일 생성, AI 분석)도 같은 URL 을 더 싸게 받는다.

### 동작 보호

| 검증 | 결과 |
|---|---|
| `R2GetObjectSignerTest` — presigner 가 찍은 서명 시각(`X-Amz-Date`)으로 시계를 고정해 직접 서명한 URL 이 **문자열로 완전히 같은지** | 15건 통과. 한글·공백·따옴표·`+%&=`·이모지·경로 문자열 파일명, Content-Type 4종, 특수문자 키, 응답 헤더 미지정 |
| `DownloadApiTest` (다건 23 · 단건 12) | 35건 통과 — 응답 계약 그대로 |
| `R2FileStorageLazyInitTest` | 2건 통과 |
| 로컬 MinIO 에 직접 서명 URL 로 GET | 200, `Content-Disposition`·`Content-Type` 이 의도대로 |
| dev(실제 R2) 배포 후 확인 | 다건 2장 → URL GET 200(`image/png`, 353KB, 파일명 일치). 단건 302 → GET 200 |

SDK 를 올려 presigner 의 서명 규칙이 바뀌면 `R2GetObjectSignerTest` 가 먼저 깨진다. 그때 직접 서명 쪽을 맞춘다.

### 해석

- **300장 다건은 확실히 줄었다.**
  - 서버 처리 시간이 네 단계 모두 약 111ms → 약 30ms 로 같은 폭(-73%) 줄었고, 앱 CPU 는 부하에 비례해 -50~-77% 줄었다.
  - 차이가 측정 잡음보다 훨씬 크다. 개선 전 값은 2주 전 #581 측정(10-22, LOAD EC2 발신: 서버 110ms, 앱 CPU 5.8·10.9·21.9·43.2%)과 몇 % 안에서 재현됐다.
  - 프로파일과도 맞는다. 서명이 CPU 의 79% 이고 서명 1회가 약 3~6배 싸졌으므로 70~80% 감소가 예상되고, 실제로 초당 8건에서 77% 줄었다.
  - 300장 요청 1건/초당 앱 CPU 증가폭은 약 5.5%p → 약 1.2%p 다. 단순 계산으로 dev 에서 300장 요청만으로 CPU 가 차는 지점이 초당 약 17건 → 약 80건으로 올라간다(다른 한계는 반영하지 않은 값).
- **10장 다건은 조금 줄었다.** 서명이 10개뿐이라 원래 효과가 작다. 서버 평균 16→14ms, 19→15ms, 앱 CPU 22.8→18.3%(초당 50건)로 나빠지지 않았고 조금 좋아진 것으로 보이지만, 잡음 범위와 겹친다.
- **DB 는 그대로다.** 커넥션 대기 0, RDS CPU 5~10% 로 전후 같은 수준이다. 이번 변경은 DB 를 건드리지 않는다.

### 10장 · 초당 50건 1차 측정을 다시 잰 이유

개선 후 1차(08:46:28 시작)는 서버 평균 40.5ms·p95 228ms, k6 p99 1,013ms·최대 3.6초로 개선 전보다 나쁘게 나왔다. 15초 단위로 나눠 보니 본 측정 첫 45초(08:47:28~08:48:13)에만 서버 평균이 74·227ms 로 튀었고 나머지 2분 15초는 14~28ms 였다.

| 같은 시각에 본 것 | 값 |
|---|---|
| dev Hikari 커넥션 새로 생성 | 08:47:15~08:49:45 에 약 16개 (1개 46~57ms) |
| dev 커넥션 획득 평균 | 31.8ms (그 외 구간 0~0.3ms) |
| dev GC 정지 최대 | 54ms |
| RDS WriteLatency 최대 | 08:48 3.1ms (앞뒤 분 0.1~0.3ms) |
| prod 요청·커넥션 획득 | 초당 0.1~0.3건, 획득 약 1ms 로 평소 수준 |

- Hikari 커넥션 수명은 기본 30분이다. 앱을 08:20 에 재시작했으므로 약 27~29분 뒤 커넥션 교체가 몰렸고, 초당 50건 부하 위에 커넥션 생성·GC 정지가 겹친 것으로 본다. 개선 전 측정에서도 재시작(04:46) 약 29분 뒤 같은 교체가 있었지만 부하가 낮은 300장 초당 2건 단계와 겹쳐 드러나지 않았다. 원인을 확정하지는 않았다.
- 같은 순서(AI 끔·앱 재생성 → JIT 예열 → 10장 초당 50건)로 재측정해 교체 시점과 겹치지 않게 했고, 위 표에는 재측정 값을 썼다. 1차 값은 기록으로만 남긴다.

### 측정 한계

- 각 단계 1회 실행이다. 300장은 효과가 커서 결론이 바뀌지 않지만, 10장의 작은 차이는 반복 측정 없이 판단하지 않는다.
- 부하를 노트북에서 보냈다(#581 은 같은 리전 LOAD EC2). LOAD EC2 의 #581 시드에는 refresh 토큰이 없어 토큰이 만료됐고, refresh 토큰이 있는 #582 시드를 썼다. 서버 지표가 #581 기록과 같은 수준으로 재현돼 서버 판단에는 영향이 없다고 본다.
- 개선 전 첫 실행(04:46~05:04)은 노트북 연결이 잠깐 끊겨 300장 초당 4건 단계에서 k6 실패 0.7%·최대 51초가 나왔다. 서버에서는 같은 구간 응답이 모두 200 이고 앱 로그에 WARN·ERROR 가 없었다. 이 실행은 버리고 처음부터 다시 쟀다.
- 개선 전·후 사이 develop 에 #673(신고 API)이 들어갔다. 다운로드 경로와 무관하다.
- #581 7절에서 "개선 후 재측정 때 다시 본다"고 한 new batch 20 단발 지연은 이번 조건(10장 초당 10·50)에 초당 20건이 없어 다시 보지 못했다. 초당 50건 재측정의 최대 지연은 서버 정상 구간에서 362ms(k6) 였다.
