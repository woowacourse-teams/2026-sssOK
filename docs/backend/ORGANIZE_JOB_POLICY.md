# 사진 정리 정책

**한 방에서 한 작업을 분석하고, 요청자가 결과를 검토한 뒤 폴더로 반영한다.**
검토는 분석 완료 후 30분까지 가능하다. 반영하거나 취소하거나 시간이 지나면 방에서 다음 작업을 시작할 수 있다.

2026-11-04 회의 기준. 정책을 읽는 문서이며, 구현·배포 완료를 뜻하지 않는다.

## 핵심 기준

| 궁금한 것 | 결정 |
| --- | --- |
| 사진은 몇 장까지? | 분석 가능한 사진 **200장** |
| 한 방에서 몇 개까지? | 분석·검토를 합쳐 **활성 작업 1개**. 과거 이력은 유지 |
| 누가 시작할 수 있나? | 방장과 참여자 모두 |
| 누가 결과를 다루나? | **작업 요청자만** 조회·검토·반영·취소·재시도 |
| 익명 회원은? | **회원 계정별·방별 1회** 체험 |
| OAuth 회원은? | 총 횟수 제한 없음. 새 요청 간격 **60초** |
| 결과는 언제까지 검토하나? | 분석 완료 후 **30분** |
| 결과 데이터는 언제까지 남나? | 분석 완료 후 **3일**. 검토 시간과 별개 |
| 진행 상황은 어떻게 아나? | 기존 방 **SSE**로 진행·완료 수신 |

위 내용은 최신 회의 결정을 따른다. 익명 체험은 이전의 ‘계정 전체에서 1회’가 아니라 **같은 계정이 같은 방에서 1회**다.
60초 간격·재시도 상한·멱등 키 보관 시간은 운영 결과에 따라 조정할 초기값이다.

## 1. 정리 요청

버튼으로 종류를 고르거나 문장으로 요청한다. 두 방식 모두 **접수 API에서 권한과 제한을 검사**한다.
별도 시작 전 확인 API(`availability`)는 없앤다.

- 업로드 완료된 JPEG·PNG 중 분석 가능한 사진을 대상으로 한다.
- 대상이 0장이거나 200장을 넘으면 거절한다. 일부만 임의로 골라 분석하지 않는다.
- 요청 시점에 대상 목록을 확정한다. 이후 업로드한 사진은 이번 작업에 추가하지 않는다.
- 권한·한도·문장 해석에서 거절되면 작업을 생성하지 않는다.

예를 들어 방의 미디어가 230개여도 분석 가능한 사진이 180장이면 한도는 통과한다.

### 회원별 사용 제한

| 구분 | 적용 방식 |
| --- | --- |
| 익명 체험 | 작업 저장 시 `(회원, 방)`의 체험 사용권 확보. 다른 방의 체험과는 독립적 |
| OAuth 새 요청 | 직전 접수 성공부터 60초. 회원 기준으로 모든 방·버튼·텍스트에 공통 적용 |
| 텍스트 해석 | 익명·OAuth 모두 회원별 분당 5회. 해석을 시도한 모호함·미지원 요청도 포함 |
| 같은 요청 재전송 | 새로운 사용으로 세지 않음 |
| 시간 제한 초과 | 429 응답. Retry-After로 남은 대기 초 안내 |

접수 검증 실패는 OAuth의 60초 간격을 새로 시작하지 않는다.
익명 체험의 **실패·취소 시 복구 방식은 아래 미정 사항**을 따른다.

## 2. 분석 진행과 화면 복원

**진행 중에는 SSE를 받고, 다시 들어왔을 때는 현재 상태를 조회한다.** 3초 주기 폴링은 하지 않는다.

| 누구에게 | 보여줄 정보 |
| --- | --- |
| 방 멤버 전체 | 방에 활성 작업이 있는지 |
| 작업 요청자 | 작업 상태·진행 단계·처리 장수·완료·실패 정보 |

프론트는 방이 사용 중이면 새 요청 버튼을 막는다. 백엔드도 같은 제한을 검사하므로 동시에 눌러도 한 작업만 접수된다.
분석이 끝나도 **검토 중이면 방은 계속 사용 중**이다.

화면에 다시 들어오거나 SSE가 재연결되면 `GET current`로 상태를 맞춘다.
내 작업이 진행 중이면 진행 화면, 검토 중이면 결과 화면, 실패했다면 실패 안내를 복원한다.
다른 사람의 작업은 상세를 보여주지 않고 버튼만 막는다.

## 3. 분석 완료와 검토

완료 알림을 받으면 결과 조회 API로 그룹별 사진을 가져온다. 이때 실제 폴더는 아직 만들지 않는다.

- **그룹이 0개여도 성공**이다. 빈 그룹 목록과 미분류·개별 오류를 보여준다.
- 검토는 분석 완료 후 30분 동안 가능하다. 화면을 다시 열거나 조회해도 연장하지 않는다.
- 시간이 지나면 `EXPIRED`로 끝내고 방의 활성 제한을 해제한다.
- 만료 후에는 결과 조회·반영을 410으로 거절한다. 새 정리를 원하면 새 작업을 접수한다.
- 0개 그룹으로 반영할 것이 없으면 취소 API로 검토를 종료할 수 있다.

### 검토 30분과 보관 3일의 차이

| 구분 | 의미 | 기한 이후 |
| --- | --- | --- |
| 검토 30분 | 사용자가 결과를 반영할 수 있는 시간 | 검토 만료, 방 해제, 반영 불가 |
| 데이터 보관 3일 | 서버가 결과 본문을 보관하는 시간 | 결과 본문 제거, 작업·실행 이력 유지 |

둘 다 분석 완료 시각부터 계산한다. 오후 3시에 완료했다면 검토는 **오후 3시 30분까지**다.
결과 본문이 3일 동안 남더라도 만료된 검토를 다시 열어 반영할 수는 없다.
이미 반영한 `APPLIED` 결과는 데이터 보관 기한까지 조회할 수 있다. 반영·취소로 보관 기간을 연장하지 않는다.

## 4. 폴더 반영

**사용자가 고른 사진으로 새 폴더를 만든다. 기존 폴더를 덮어쓰거나 병합하지 않는다.**

1. 요청자가 그룹별 사진을 선택하고 폴더 이름을 정한다.
2. 프론트가 기존 폴더 목록과 비교해 중복 이름이면 변경을 안내한다.
3. 서버가 이름·사진·권한·검토 기한을 다시 확인한다.
4. 모두 유효하면 폴더 생성과 사진 연결을 한 번에 반영하고 방을 해제한다.

반영 대상은 **groupId가 있는 일반 그룹만**이다. 소그룹·미분류는 조회용이다.
검토 중 사진이 삭제됐거나 같은 폴더명이 생겼다면 반영을 거절한다. 일부 폴더만 만들어진 상태로 끝내지 않는다.

## 5. 취소

| 현재 상황 | 취소 결과 |
| --- | --- |
| 접수 대기·분석 중 | CANCELED, 방 해제 |
| 결과 검토 중 | 검토 포기, 방 해제 |
| 이미 취소·실패·만료 | 기존 상태 그대로 반환 |
| 이미 반영 완료 | 취소 불가 |

취소는 요청자만 할 수 있다. 분석 서버에 중단 기능이 없어 계산은 계속될 수 있지만 늦게 도착한 결과는 버린다.
취소 API는 이미 만든 폴더를 되돌리는 기능이 아니다.

## 6. 재시도

**다시 하면 해결될 수 있는 실패만 같은 작업 ID로 재시도한다.**

| 상황 | 처리 |
| --- | --- |
| 작업 저장 전 접수 실패 | 작업 ID가 없으므로 원래 접수 API로 다시 요청 |
| 전달 실패·MCP 접수 여부 불명 | 같은 실행 ID로 재전송. 새 분석을 만들지 않음 |
| 기존 실행이 확실히 끝난 일시적 실패 | 같은 작업에 새 실행 회차 생성 가능 |
| 이미 분석 중·검토 가능 | 현재 상태 반환. 중복 실행 없음 |
| 취소·반영·만료 또는 해결되지 않은 설정·대상 오류 | 재시도 불가 |

- 새 실행을 만드는 사용자 재시도는 **작업당 최대 3회**다. 최초 실행을 포함해 최대 4회다.
- 재시도 대기는 순서대로 **5초 → 15초 → 45초**다.
- 같은 실행의 재전송과 자동 발송 재시도는 이 횟수에서 제외한다.
- 횟수를 다 쓰면 재시도 불가다. 새 작업은 회원 제한과 방 활성 제한을 다시 통과해야 한다.
- 원격 분석의 종료가 확인되지 않았다면 타임아웃만 보고 새 실행을 만들지 않는다.
- 사진 목록은 처음 요청한 그대로 유지한다. 새 사진을 포함하려면 새 작업이 필요하다.

화면은 `retryable`과 `retryAvailableAt`으로 버튼과 대기 시간을 표시하고 서버가 호출 시 다시 검사한다.

## 7. 같은 요청이 여러 번 도착하면

접수·재시도·폴더 반영에 **요청 식별 키(Idempotency-Key)**를 사용한다.
응답이 유실돼 다시 보내더라도 같은 작업이나 폴더가 중복 생성되지 않게 하기 위한 규칙이다.

- 같은 키·같은 입력: 다시 실행하지 않고 기존 처리 결과를 사용한다.
- 같은 키·다른 입력: 409로 거절한다.
- 성공한 요청만 24시간 기록한다. 검증 실패·429·503은 기록하지 않는다.
- 기록된 재전송은 사용 횟수와 시간 제한에 추가 반영하지 않는다. 인증·소유권 검사는 계속 적용한다.

## 구현 시 유지할 규칙

- 작업은 사용자 요청, 실행은 분석 시도다. 허용된 재시도만 `FAILED → QUEUED`로 돌아가며 새 실행 회차를 만든다. 완료 이벤트가 먼저 오면 `QUEUED → READY`도 허용한다.
- `QUEUED`·`RUNNING`·`READY`는 방을 점유하고, `FAILED`·`CANCELED`·`APPLIED`·`EXPIRED`에서 해제한다.
- 검토 기한은 스위퍼뿐 아니라 API에서도 검사한다. 반영·취소·만료의 경합은 조건부 상태 변경이나 잠금으로 제어한다.
- 멱등 기록은 실제 변경과 같은 트랜잭션에 저장하고 `(회원, 방, 연산, 키)`의 유일성을 보장한다. 재전송 확인은 사용 제한 검사보다 먼저 하되 인증·소유권 검사는 생략하지 않는다.
- 키 보관 기한이 지나도 활성 작업 제한과 상태 검사로 중복 실행·반영을 막는다.
- SSE 수신자 필터는 실시간 전송과 저장된 이벤트 재전송에 동일하게 적용한다. 알림은 DB 커밋 뒤 발행한다.
- 최초 연결·재연결은 SSE 수신을 준비한 뒤 `GET current`로 복원하고 `jobVersion`·`roomVersion`으로 오래된 갱신을 무시한다. 커밋 직후 알림 유실도 이 스냅샷으로 보정한다.
- 내부 분석 이벤트는 전용 Bearer 인증을 사용한다. 다른 실행 회차·중복·늦은 이벤트는 상태를 바꾸지 않고 ack하며, 응답은 DB 커밋 뒤 반환한다. 형식은 [MCP 계약](../../mcp/SERVER_CONTRACT.md)을 따른다.
- 서명 URL은 발송 시 생성하고 DB에 저장하지 않는다. 서명 URL과 내부 토큰은 모델에 전달하지 않으며 모델은 도구 선택만 한다.

## 남은 확인 사항

### 익명 체험의 복구와 취소 처리 — 세부 제안

체험이 회원·방별 1회이고 작업 저장 때 사용권을 확보한다는 점은 확정이다. 아래는 아직 세부 제안이다.

| 상황 | 제안 |
| --- | --- |
| 저장 전 거절 | 차감하지 않음 |
| 같은 작업 재시도 | 추가 차감하지 않음 |
| 분석 성공, 0개 그룹 포함 | 체험 사용 처리 |
| MCP 접수 전 취소 | 사용권 확보 해제 |
| MCP 접수 후 사용자 취소 | 체험 사용 처리 |
| 최종 FAILED | 사유와 관계없이 체험 복구 |

실패 후 재시도한다면 같은 `(회원, 방)`의 사용권을 다시 확보해야 한다.
그사이 새 작업이 사용권을 가져갔다면 이전 작업의 재시도를 거절한다.
익명 계정이 OAuth로 바뀌면 접수 시점의 회원 유형을 따른다. 계정 생성·탈퇴 우회 방지는 별도 범위다.

### 구현·운영 확인

- Spring과 Python의 사진 한도를 모두 200장으로 맞추고 실제 환경에서 처리 시간·자원을 검증한다.
- #659와 #660은 한 PR 범위로 정리했다. 변경이 너무 크면 리뷰를 위한 분리 여부를 다시 판단한다.
- 이력의 영구 삭제 정책은 이번에 새로 정하지 않았다.
