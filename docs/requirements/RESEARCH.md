## 1. 문제 정의

**단체 사진 공유는 "보내는 쪽"과 "받는 쪽" 양쪽 모두에서 불편하다.**

1차 인터뷰 9건(2026.07.13~16, 6명 + 심층 3명)에서 반복적으로 확인된 불편을 다섯 갈래로 정리했다.

### 1) 보내기가 막힌다

| 상황             | 실제 사례                                                                               |
| ---------------- | --------------------------------------------------------------------------------------- |
| 첨부 개수 제한   | 모카 - 45장을 20/20/5로 세 번에 나눠 전송, 드래그 범위를 헷갈림                         |
| 분할 전송 실패   | 피즈 - 10장씩 나눠 보냈으나 앞 2건만 전송되고 나머지 로딩 실패, 결국 공유 자체를 포기   |
| 대용량 영상      | 러로 - 슬랙으로 영상 전송 시 용량 때문에 대기 시간이 지나치게 길어짐                    |
| 우회 경로도 막힘 | 피즈 - 구글 드라이브 앱 미설치 시 저장/업로드 버튼 자체가 뜨지 않아 사진을 한 장씩 저장 |

### 2) 받기·다시 찾기가 불편하다

- 사진이 채널·스레드·DM으로 흩어져 나중에 유실된다. 모카는 과거 사진을 즐겨찾기와 날짜에 의존해 겨우 찾아냈다.
- 피즈는 누가 자기 사진을 찍었는지 몰라서 재요청조차 하지 못했다.
- 러로는 뭉텅이로 쏟아진 사진은 아예 열어보지 않는다고 답했다.

### 3) 대안으로의 전환도 불편하다

- 카카오톡 전환은 번호·프로필 공개를 전제하므로, 아직 친하지 않은 공적 관계에서는 부담이다. 러로의 표현으로는 _"카톡이 없는 사이면 거리가 있는 사이"_ 다.
- 에어드롭은 1:1이라 다수 대상 공유의 대안이 되지 못한다.

### 4) 대용량 사진은 미리보기조차 어렵다

사진 용량이 크면 미리보기가 제한되어 내용을 바로 확인할 수 없고, 무엇이 담겼는지 보려면 다운로드가 사실상 필수가 된다. 확인·선택 전에 불필요한 다운로드를 강요받는다.

### 5) 한 장을 고르기 위해 전체를 받아야 한다

원하는 사진 한 장만 확인하려 해도 전체 사진을 통째로 내려받은 뒤 그 안에서 일일이 골라내야 한다. 필요한 사진만 선택적으로 보고 받는 흐름이 없어 탐색 비용이 크다.

### 2차 조사에서 추가된 근거 - 콘텐츠 취합 관점 (홍보대사)

1차 조사가 "참여자" 입장의 불편이었다면, 2차 조사는 촬영본을 **모아서 콘텐츠로 만드는 담당자** 입장에서 같은 문제를 다시 확인했다. 흐름 자체가 취합 단계에서 깨진다.

```
행사 촬영 (20~30명이 각자 폰으로)
        ↓
   ✗ 여기서 깨진다  ← 취합
        ↓
콘텐츠팀 편집 → 인스타 · 학교 채널 업로드
```

취합 단계에서 쓰는 도구 셋이 모두 실패한다.

| 도구         | 실패 방식                                                                                  | 결과                             |
| ------------ | ------------------------------------------------------------------------------------------ | -------------------------------- |
| **밴드**     | 업로드 시 화질 깨짐                                                                        | 도구 폐기됨                      |
| **에어드롭** | 1:1이라 다수에게 못 보냄. 긴 영상은 대기 시간 과다                                         | 실질적으로 사용 불가             |
| **카카오톡** | 대용량 전송 느림 + 앱을 벗어나면 전송 중단 → 창을 붙잡고 대기 + 전송 실패 잦음 + 화질 깨짐 | 가장 많이 쓰지만 가장 고통스러움 |

근거 있는 통증 (카피·기능 판단에 그대로 쓸 수 있는 것들):

| 통증                                                              | 출처            |
| ----------------------------------------------------------------- | --------------- |
| 카톡 대용량 전송 중 **앱을 벗어나면 멈춤** → 채팅창에 붙잡혀 대기 | 홍보대사        |
| 반복 전송 → **전송 실패 잦음**                                    | 홍보대사 · 피즈 |
| 밴드 업로드 시 화질 저하 → **도구 폐기**                          | 홍보대사        |
| 카톡·밴드 경유 영상은 화질이 깨져 **편집 소재로 못 씀**           | 홍보대사        |
| 에어드롭이 1:1이라 다수에게 못 줌                                 | 홍보대사 · 러로 |
| 긴 영상은 에어드롭 전송 대기 시간 과다                            | 홍보대사 · 러로 |
| 첨부 개수 제한 — 45장을 20/20/5로 3회 분할 전송                   | 모카            |
| 분할 전송 실패 → 공유 자체를 포기                                 | 피즈            |
| 드라이브 앱 미설치 시 업로드 버튼 자체가 안 뜸                    | 피즈            |
| 채널·스레드·DM으로 흩어져 유실                                    | 모카            |
| 뭉텅이로 쏟아진 사진은 아예 안 열어봄                             | 러로            |
| 한 장 고르려고 전체를 내려받아야 함                               | —               |

### "화질" 클레임 규칙

기존에는 "원본 화질"을 인터뷰 근거 없음으로 보고 카피에서 금지했으나, 이번 조사에서 화질이 도구를 실제로 버린 사유로 두 번 등장했다. 규칙을 폐기하는 게 아니라 **조건부로 바꾼다.**

- 금지 유지: 일반 사용자 대상 "예쁜 사진을 원본 화질로" 류의 카피. 여전히 근거 없음
- 허용: **편집 소재로서의 원본 보존.** 콘텐츠 제작 워크플로 맥락에 한정

### 여전히 근거 없음 (금지 유지)

- **"아이폰 ↔ 안드로이드"**: 통증의 실체는 기종 차이가 아니라 에어드롭이 1:1이라 다수에게 못 준다는 것
- **"새 사진이 올라온 걸 몰라서 안 본다"**: 인터뷰가 지지하지 않는다. 러로의 "뭉텅이면 안 열어본다"는 알림 부재가 아니라 **탐색 비용** 문제이다. 알림을 붙여도 안 열어본다. 단, [해결책 검증](#6-해결책-검증--1차-프로토타입-테스트)의 테스트 2는 "올라온 걸 알리면 재입장한다"는 좁은 행동만 확인한 것이고 이 클레임과 상충하지 않는다. 알림은 방에 들어오게는 하지만, 들어온 뒤 뭉텅이를 훑어보게 만드는 것은 별개 문제(→ 미리보기·선택 다운로드로 해결)다.

풀리지 않는 의문점 (1차 조사 시점 가정 · 아직 완전히 정리되지 않음):

1. 이미지·사진 공유 니즈는 카톡·슬랙 등 기존 SNS를 벗어날 만큼 크다.
2. 사람들이 이미지 공유를 꺼리는 것은 분류·업로드·다운로드 같은 번거로운 작업이 많기 때문이다.

## 2. 목적 및 지향점

**관계를 전제하지 않고, 한곳에 사진을 모으고, 각자의 이득을 취한 뒤 사라지는 공유 공간을 만든다.**

별도 앱 설치나 번호 교환 없이, 링크 하나로 여러 명이 부담 없이 사진·영상을 모으고 나눠 가질 수 있는 단발성 공유 서비스. 카톡처럼 관계를 전제하지 않고, 슬랙처럼 흩어지지 않으며, 이벤트/모임이 끝나면 자연스럽게 사라지는 가벼운 방식을 지향한다.

| 기존 채널     | 한계                               | 쏙의 지향                        |
| ------------- | ---------------------------------- | -------------------------------- |
| 카카오톡      | 번호·프로필 공개 = 관계를 전제     | 링크만 있으면 익명 게스트로 참여 |
| 슬랙          | 채널·스레드·DM으로 분산, 첨부 제한 | 이벤트 단위 방 하나에 전부 집결  |
| 구글 드라이브 | 앱 설치·계정 로그인 필요           | 설치·가입 없이 웹 링크로 즉시    |

### 서비스 흐름

이벤트가 끝난 직후, 주최자가 링크 하나를 던진다. 참여자는 그 링크를 눌러 이름만 입력하고 들어와 사진을 올리고, 원하는 사진을 골라 받아 간다. 정해진 시간이 지나면 방과 데이터는 전부 사라진다.

## 3. 차별화 전략

### 참고한 방식

인공눈물 시장에는 이미 인지도가 굳은 브랜드들이 있었지만, 후발 주자인 아이드롭은 "무방부제"라는 속성 하나만 걸고 들어와 자리를 잡았다. 성분표 전체로 겨루지 않았고, 눈에 좋은 이유를 나열하지도 않았다. 한 칸이 비어 있다는 것만 보여줬다.

이게 통한 이유는 셋이고, 쏙에 그대로 옮길 수 있다.

1. **이진값이다.**

- 있냐 없냐. "더 좋다"는 비교가 아니라 "없다"는 사실이라 반박할 여지가 없다.

2. **뺀 것으로 이긴다.**

- 더 넣어서 이기려면 예산 싸움이 되지만, 빼는 건 후발 주자도 할 수 있다.

3. **기존 강자가 구조적으로 못 따라온다.**

- 방부제는 유통·보관 구조 때문에 넣을 수밖에 없었다. 따라 하려면 제품 구조 자체를 바꿔야 한다.

3번이 핵심이다. 전략은 우리가 잘하는 것이 아니라 상대가 구조적으로 못 하는 것이어야 한다. 잘하는 것으로 잡으면 자본 있는 쪽이 따라와서 덮는다.

### 후보 속성 비교

| 후보 속성                  | 이진값인가 | 상대가 못 따라오나                                    | 근거                       | 판정                                |
| -------------------------- | ---------- | ----------------------------------------------------- | -------------------------- | ----------------------------------- |
| **원본 그대로 (무압축)**   | ○          | **◎ 카톡·밴드는 압축이 비용 구조 그 자체**            | 밴드 폐기 · 영상 편집 불가 | **채택**                            |
| 전송이 안 끊긴다           | ○          | ○ 카톡 앱 구조 문제                                   | 홍보대사                   | 2순위 (인프라 약속이라 지키기 부담) |
| 설치·로그인 없이 링크 하나 | △          | ✕ 드라이브도 링크는 준다. 단, 이메일을 초대해야 한다. | 피즈                       | 보조                                |
| 필요한 것만 골라 가기      | ✕          | △                                                     | 미검증 (H5)                | 쐐기로 쓰기엔 이르다                |

### 쏙의 전략 - 원본 그대로

카카오톡과 밴드는 압축을 뺄 수 없다. 수천만 명의 트래픽 비용이 압축 위에 서 있기 때문이다. 쏙은 한 번에 일단 한 팀만 감당하면 되니까 뺄 수 있다. 이건 기술적으로 뛰어나서가 아니라 규모가 작아서 가질 수 있는 우위이고, 후발 주자가 가질 수 있는 우위는 원래 이 종류뿐이다.

**대상에게 던질 한 문장**

> 카톡으로 받은 사진으로는 편집을 못 해요. 쏙은 **찍은 그대로** 옵니다.

단, 이 말은 아무에게나 통하지 않는다. "원본 화질"은 일반 사용자에게는 여전히 와닿지 않고, **직접 편집하는 사람에게만** 통한다. 그래서 이 쐐기는 [타겟층 정의](#4-타겟층-정의-3주차-한정)에서 좁혀둔 타겟과 떼어놓을 수 없다. 타겟을 넓히는 순간, 이 말도 같이 무뎌진다.

### 규모가 커지면 원본을 못 버티지 않나

가장 자주 나오는 반론이다. 사용자가 늘면 무압축 저장·전송 비용이 결국 감당이 안 되고, 그러면 우리도 카톡처럼 압축하게 되는 것 아니냐는 것이다.

답은 **비용이 누적 업로드량이 아니라 동시에 살아있는 데이터 총량에 비례한다**는 데 있다. 방은 24시간 뒤 사라진다. 그러니 저장량은 쌓이는 게 아니라 **회전한다.**

행사 1건을 30명 × 사진 50장, 대략 10~20GB로 잡으면, 동시에 100건이 굴러가도 어느 시점의 보관량은 1.5TB 남짓이고 그마저 하루 뒤 비워진다. 다운로드는 트래픽 비용이 무료인 저장소(현재 R2)를 쓰는 한 비용에 잡히지 않는다. 가장 무거운 쪽이 공짜다.

카카오톡이 압축을 못 빼는 이유는 트래픽이 많아서가 아니라 **수억 명의 것을 영구히 들고 있어야 하기 때문**이다. 쏙은 하루 뒤 버린다. 앞의 "3. 기존 강자가 구조적으로 못 따라온다"의 실체가 이것이다. → 우리가 뛰어나서가 아니라, 버리는 서비스라서 안 버리는 서비스가 못 하는 걸 할 수 있다.

**다만 이 계산은 세 가지가 지켜질 때만 성립한다.**

1. **만료 삭제가 실제로 작동해야 한다.** 안 되는 순간 비용 모델이 회전에서 누적으로 바뀌고, 위 논리 전체가 무너진다. 이건 "핵심 약속을 못 지키는 것"을 넘어 **쐐기의 경제적 근거가 사라지는 것**이다. → [features/001-room.md](./features/001-room.md)
2. **삭제 후 보관 기간이 만료 시간을 지배하면 안 된다.** 지금 스펙은 만료 24시간인데 삭제 후 30일 보관이라, 실질 보관 기간이 30배로 늘어난다. 복구 목적이라면 원본 전체가 아니라 축소본만 남기는 등, 보관 기간과 보관 대상을 함께 재검토해야 한다.
3. **트래픽 비용이 0에 가까운 저장소를 계속 써야 한다.** 여기서 이탈하면 다운로드가 곧바로 비용이 된다.

**약속의 경계를 분명히 한다.** 쏙이 파는 것은 "원본을 영구 보관한다"가 아니라 **"방이 살아있는 동안은 찍은 그대로"**다. 이건 약속을 몰래 좁히는 게 아니라 서비스 정의 그 자체다 — 사라지는 게 원래 기능이다.

정말로 규모 때문에 못 버티는 날이 오면, 그때 버릴 것은 쐐기가 아니라 **경계**다. 방당 총 용량 상한, 만료 기간 단축, 원본과 미리보기의 보관 기간 분리 — 쐐기를 유지한 채 비용을 묶는 수단이 먼저다. 쐐기 자체의 교체는 비용 때문이 아니라 [H4가 실패했을 때](./VALIDATION-PLAN.md#h4--쐐기-검증--원본-보존이-도구-선택의-결정-요인이다)만 한다.

### 규율 — 말하지 않을 것

쐐기의 절반은 **나머지를 말하지 않는 것**이다. 기능을 넷 다 말하면 하나도 안 남는다.

- 첫 접촉(랜딩 히어로, 첫 한 마디)에서는 **원본 보존 하나만** 말한다.
- 골라 담기 · QR · 링크 배포는 **들어온 다음에** 보여준다. 유인이 아니라 유지 장치다.
- **"편하다" "간편하다" 류의 형용사 금지** - 모든 경쟁자가 이미 그렇게 말하고 있고, 이진값이 아니라서 검증도 반박도 안 된다.

### 쐐기가 틀렸다면

[H4](./VALIDATION-PLAN.md#h4--쐐기-검증--원본-보존이-도구-선택의-결정-요인이다)가 실패하면(콘텐츠팀이 결국 카톡 파일로 편집) 쐐기를 **전송이 안 끊긴다**로 교체한다. 그 경우 이 절만 갈아끼우고 [타겟층 정의](#4-타겟층-정의-3주차-한정)와 [측정 지표](./VALIDATION-PLAN.md#5-측정-지표)는 유지한다.

## 4. 타겟층 정의 (3주차 한정)

> **여러 명이 찍은 촬영본을 한 명이 모아서 콘텐츠로 만드는 팀**

1차 진입점은 **대학 홍보대사 · 학생회 홍보부**다. 다만 타겟을 "학교 홍보대사"라는 소속이 아니라 **취합해서 콘텐츠를 만드는 역할**로 정의한다. 같은 카피 한 벌로 동아리 홍보팀·공연팀까지 커버되고, 학교당 한 팀이라는 표본 한계도 풀린다.

### 첫 유저는 "찍는 사람"이 아니라 "모으는 사람"

| 역할                 | 인원    | 하는 일                                 | 우선순위                                       |
| -------------------- | ------- | --------------------------------------- | ---------------------------------------------- |
| **취합·콘텐츠 담당** | 1~3명   | 공유방 생성, 링크 배포, 골라 담기, 편집 | **첫 유저 — 랜딩과 제품은 이 사람에게 말한다** |
| 촬영 참여자          | 20~30명 | 링크 받고 업로드                        | 획득 대상. 마찰이 0이어야 함                   |

### 왜 이 집단인가?

1. **행동이 확인됐다.** "밴드는 화질 깨져서 지금 안 쓰고 있고" — 불만이 아니라 도구 폐기까지 간 이력이 존재한다.
2. **요청하지 않았는데 통증을 길게 쏟아냈다.** 유도 질문에서 나온 통증과 무게가 다르다.
3. **반복된다.** 행사마다 발생한다. 리텐션 측정이 가능한 최소 빈도를 넘긴다.
4. **취합 담당자가 조직적으로 존재한다.** 첫 유저를 특정할 수 있다.
5. **확산 구조가 있다.** 학교 간 교류 + 기수 인수인계 → 매년 새 기수가 같은 문제를 반복한다.
6. **타이밍이 맞다.** 9월 개강 시즌(개강총회·OT·신입 모집·축제)이 활동 성수기 직전이다.

### 명시적 제외 (1차에서 안 건드림)

| 제외 대상                  | 이유                                                                               |
| -------------------------- | ---------------------------------------------------------------------------------- |
| 사내 워크숍                | 회사 보안정책이 외부 스토리지 링크를 차단. 제품이 아니라 IT 부서와 싸우게 됨       |
| 학회 · 컨퍼런스            | 연 1~2회. 리텐션 측정 불가                                                         |
| 유치원 · 어린이집 ↔ 학부모 | 통증은 가장 크나 아동 사진. 지금 1차 MVP가 감당할 리스크가 아님                    |
| 웨딩 · 돌잔치 · 여행       | 공적 관계 정의와 불일치. 경쟁 포화 → 나중에 도전                                   |
| 러닝크루 · 운동 소모임     | **2차 후보로 보류** ([검증 계획 4장 C단계](./VALIDATION-PLAN.md#4-검증-단계) 참조) |

> 1차 조사 시점에는 우테코 마을·크루 단위 모임, 동아리, 사내 팀·TF, 결혼식 등을 폭넓게 확장 후보로 봤다. 2차 조사를 거치며 대부분이 위 표처럼 명시적 제외로 좁혀졌다 — 우테코 크루는 **검증 대상이 아니라 리허설 대상**으로 재분류됐다([검증 계획 4장 A단계](./VALIDATION-PLAN.md#4-검증-단계)).

더 자세한 내용은 [초기 MVP 타겟층](https://app.notion.com/p/MVP-3bb6aca63df48016b5c6d5ba7fb15c41?pvs=21) 페이지를 참고한다.

## 5. 문제 검증 — 1차 인터뷰

타겟 유저 9명을 대상으로 "최근 사진 공유 경험 / 사진 유실·탐색 / 채널 선택 이유" 3주제로 인터뷰하고 데모를 시연했다.

- **모카**: 슬랙 첨부 제한 때문에 45장을 20/20/5로 나눠 보냄, 사진이 여러 채널에 흩어져 즐겨찾기+날짜로 겨우 탐색, 에어드롭은 1:1이라 대안이 안 됨
- **피즈**: 드라이브 앱 미설치가 장벽, 슬랙 분할 전송 실패로 공유 자체를 포기한 경험, 누가 자기 사진을 찍었는지 몰라 재요청조차 못 함
- **러로**: 카톡이 화질·속도 면에서 최우선이고 슬랙은 차선책, "카톡이 없는 사이는 거리가 있는 사이"라 공적 관계에서 카톡 전환은 부담

세 명 모두 문제 자체는 겪고 있었지만 문제 강도에는 편차가 있었다 (러로는 필요성 자체에 의문을 제기하기도 함).

## 6. 해결책 검증 — 1차 프로토타입 테스트

**핵심 가설**: 링크 기반의 단발성 공유 공간이 있으면, 사람들이 슬랙/카톡 대신 실제로 이걸 사용해 사진을 모으고 받아갈 것이다.

기능을 코딩하지 않고 사람이 대신 수행하는 방식(Wizard of Oz)으로, 구현 비용 없이 가정만 검증했다.

|                  | 테스트 1 — 전환                  | 테스트 2 — 인지                  | 테스트 3 — 마찰                          |
| ---------------- | -------------------------------- | -------------------------------- | ---------------------------------------- |
| **시점**         | 이벤트 직후                      | 다음 날 아침                     | 다음 날 아침                             |
| **행동**         | 링크만 던지고 방치               | 슬랙에 수기로 1회 알림           | 정리 요청을 사람이 대신 처리             |
| **대상**         | 사진을 가진 참여자 전원          | **비업로더**(관객)               | 업·다운로드가 번거로운 사람              |
| **정량 지표**    | 업로더 수 / 카톡·슬랙 누수 인원  | 24시간 내 입장한 비업로더 수     | 정리 요청 인원 / 실제 다운로드 완료 인원 |
| **통과 기준**    | 업로더 5명 이상                  | 비업로더 절반 이상 입장          | 대상자 절반 이상 요청 + 수령             |
| **탈락 시 해석** | 슬랙·카톡으로 충분 → 방향 재검토 | 문제는 인지가 아니라 **동기**    | 정리 자동화 니즈 약함 → 기능 재검토      |
| **정성 질문**    | "왜 여기 말고 카톡에 올렸어요?"  | "몰랐다" vs "알았는데 굳이" 구분 | "직접 하면 몇 분 걸릴 것 같아요?"        |

### 결과

테스트 1, 2는 통과했다. 필요한 상황에서는 과반수 이상이 실제 업로드·다운로드까지 이어졌고, 수기 알림 후 비업로더의 재입장도 확인됐다.

> 참여를 막는 것은 서비스의 매력이 아니라 "새 사진이 올라왔다"는 사실의 전달이었다. 알림은 부가 기능이 아니라 이 서비스의 작동 조건에 가깝다.

테스트 3(정리 자동화 니즈)는 MCP 기반 정리 플로우 구현 이후 별도로 검증할 예정이다.

**동시에 확인된 한계**: 알림 없이 방치했을 때는 참여가 눈에 띄게 저조했다. 즉 쏙은 "쓰고 싶은 서비스"라기보다 "누가 알려주면 쓰는 서비스"에 가까운 상태이며, 이것이 매력 부족인지 습관 미형성인지는 이번 1차 조사만으로는 미판별이었다. (2차 조사에서 "탐색 비용" 쪽에 더 가깝다는 단서가 나왔다 — [1장](#여전히-근거-없음-금지-유지) 참고.)

## 7. 유저를 모을 가능성

- 인터뷰 9명 전원이 슬랙 이미지 공유 관련 불편을 실제로 겪고 있음을 확인했다.
- 이벤트 직후 실제 단체에 프로토타입 링크를 공유한 검증에서, 필요한 상황일 때 참여자 과반수 이상이 실제로 업로드·다운로드 행동까지 이어졌다.
- 모카는 데모 사용 후 서비스를 자발적으로 "셰어드롭"이라 부르며 폴더 분류 기능에 긍정적으로 반응했고, 러로는 대용량 영상 공유 상황에서 "그때 이게 있었다면 더 편리했을 것"이라며 가장 강하게 공감했다.

## 8. 다음 액션 — 2차 검증 계획

1차 조사로 사진 공유 과정에 실제 불편이 존재한다는 점은 확인했지만, 사용자에게 가장 중요한 문제가 단순한 개수 제한은 아니라는 점도 함께 확인했다. 따라서 다음 단계에서는 바로 기능을 추가하기보다, 이번 조사에서 반응이 좋았던 요소를 중심으로 프로토타입을 다시 만들어 실제 사용 상황에서 검증한다. 지금 단계의 질문은 더 이상 **통증이 있는가**가 아니다(확인됐다). 질문은 다음이다.

> **주최자가 링크를 뿌렸을 때, 초대받은 사람들이 실제로 올리는가. 그리고 그게 다음 번에도 반복되는가.**

검증 단위는 **사람 1명이 아니라 행사 1건**이다. 취합 담당자 한 명을 확보하면 20~30명이 딸려 들어온다.
