# 요구사항 문서

sssOK 서비스의 PRD(제품 요구사항 문서), 기능 명세, 화면 정의서 등 "무엇을, 왜 만드는가"에 대한 문서를 이 폴더에 둔다.

## 구조

```
docs/requirements/
├── PRD.md              ← 루트 문서. "왜 · 누구 · 핵심 가치" + 아래 문서들로 가는 링크 모음
├── RESEARCH.md         ← PRD의 근거: 인터뷰, 경쟁 비교, 차별화 전략, 검증 결과, 열린 논의
├── VALIDATION-PLAN.md  ← 2차 검증 계획: 가설(H1~H6), 검증 단계, 측정 지표
├── features/            # 기능이 무엇을 하는지 (영역별)
│   ├── 001-room.md
│   ├── 002-upload.md
│   ├── 003-selection-download.md
│   ├── 004-gallery-organize.md
│   └── 005-smart-organize.md
└── screens/              # 어떤 화면이 있고, 화면 사이를 어떻게 오가는지
    ├── 001-home.md
    ├── 002-room-entry.md
    ├── 003-gallery.md
    ├── 004-lightbox.md
    └── 005-room-settings.md
```

- **파일명 규칙**: `NNN-슬러그.md` (세 자리 번호 + 하이픈 + 영문 소문자). 번호는 우선순위/읽는 순서를 나타낸다.
- `features/`, `screens/`의 정확한 개수·이름은 시작점일 뿐, 작성하면서 자연스럽게 늘거나 합쳐져도 된다.
- **상태 표시**: 각 문서의 절마다 `**상태: 구현됨 / 미구현 / 미정 / 문제 있음**`을 붙인다. 기준은 실제 코드이며, 각 값의 뜻은 [PRD.md — 상태 표시의 뜻](./PRD.md#상태-표시의-뜻)에 정리했다.

## 작성 원칙

- **복잡하지 않게** — API, 상태 머신, 값 객체 같은 개발 용어는 쓰지 않는다.
- **제한하지 않게** — "이렇게 구현해라"가 아니라 "이런 걸 원한다"는 의도 위주로 쓴다.
- **간단하게** — 세세한 예외 케이스까지 미리 다 정하지 않아도 된다. 애매한 부분은 추후에 의논하며 채운다.
- **비개발자도 이해할 수 있게** 쓴다.

## 시작점

- [PRD.md](./PRD.md)부터 읽는다. 왜 만드는지, 누구를 위한 것인지, 핵심 가치가 뭔지 나온 뒤 features/·screens/ 목차로 이어진다.

백엔드/프론트엔드 API 계약 문서(`SPEC-BACKEND.md`, `SPEC-FRONTEND.md` 등)도 여기에 추가 예정이다.
