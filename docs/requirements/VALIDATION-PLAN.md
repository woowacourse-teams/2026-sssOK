# 검증 계획 — 2차 검증

문제 정의·타겟·쐐기 전략의 배경은 [RESEARCH.md](./RESEARCH.md)를 참고한다. 이 문서는 그 다음 단계 — **어떤 가설을, 어떤 순서로, 무엇을 보고 판정할지**만 다룬다.

1차 조사로 사진 공유 과정에 실제 불편이 존재한다는 점은 확인했지만, 사용자에게 가장 중요한 문제가 단순한 개수 제한은 아니라는 점도 함께 확인했다. 따라서 다음 단계에서는 바로 기능을 추가하기보다, 이번 조사에서 반응이 좋았던 요소를 중심으로 프로토타입을 다시 만들어 실제 사용 상황에서 검증한다. 지금 단계의 질문은 더 이상 **통증이 있는가**가 아니다. 질문은 다음이다.

> **주최자가 링크를 뿌렸을 때, 초대받은 사람들이 실제로 올리는가. 그리고 그게 다음 번에도 반복되는가.**

검증 단위는 **사람 1명이 아니라 행사 1건**이다. 취합 담당자 한 명을 확보하면 20~30명이 딸려 들어온다.

---

## 1. 프로토타입에 담을 것

이번 조사에서 반복적으로 확인된 요구를 중심으로 구성한다. 새롭게 임의로 기능을 추가하지 않는다.

- 개수 제한 없이 여러 장의 사진을 한 번에 공유
- 원본 화질 그대로 공유
- 받기 전에 어떤 사진이 있는지 미리 확인
- 필요한 사진만 골라 한 번에 받기
- 링크만 있으면 별도의 계정이나 연락처 교환 없이 공유

핵심 강점은 **원본 화질 유지 · 필요한 사진만 골라 받기 · 미리보기 · 계정 교환 없는 링크 공유** 네 가지로 잡는다. 실제 사용자 응답에서 반복해서 나타난 요구이지, 새로 지어낸 기능이 아니다.

---

## 2. 사용 행동 확인 방식

"좋아 보인다"는 의견이 아니라 실제 행동을 관찰한다. 여행·모임 후 여러 장의 사진을 공유하는 상황을 제시하고, **사진 선택 → 업로드 → 링크 공유 → 사진 확인 → 원하는 사진 다운로드** 과정을 직접 수행하게 한다. 이 과정에서 어디서 막히는지, 기존 카카오톡·에어드롭보다 과정이 간단해졌는지를 확인한다.

---

## 3. 가설과 판단 기준

> ⚠️ 아래 숫자는 **제안값**이다. 한 팀이 20~30명이라 비율이 크게 흔들리므로 비율과 절대 인원을 함께 본다. 착수 전 팀 합의가 필요하다.

#### H1 · 진입 마찰 — 설치·로그인 없는 링크면 참여자가 실제로 올린다

- 측정: 링크 배포 인원 대비 1명 이상 업로드한 인원 비율
- 성공 60% 이상 · 실패 30% 미만
- 실패 시: 마찰이 링크 이후에 있다는 뜻. 온보딩·업로드 화면 재설계
- 주의: 조직 강제력으로 올렸을 수 있음 → H3와 반드시 함께 해석

#### H2 · 재사용 — 취합 담당자가 다음 행사에도 다시 쓴다

- 측정: 2회차 행사에서 **우리가 먼저 연락하기 전에** 재요청이 오는가
- 성공: 자발적 재요청 · 실패: 우리가 물어봐야 씀
- 실패 시: 1회성 도구. 리텐션이 없으므로 제품 방향 재검토

#### H3 · 자생적 획득 — 초대받았던 참여자가 스스로 새 공유방을 만든다

- 측정: 참여자 → 생성자 전환 건수
- 성공: 행사 1건당 최소 1건 · 실패: 0건
- 왜 중요한가: 이게 되면 받는 사람이 다음번 만드는 사람이 되면서 저절로 번진다. 안 되면 한 팀씩 영업해야 하는 제품이고, **우테코 기간 안에 지표가 안 나온다**
- **이 문서에서 가장 중요한 가설**

#### H4 · 쐐기 검증 — 원본 보존이 도구 선택의 결정 요인이다

- 측정: 1호 케이스에서 **기존 방식(카톡)과 병행** 운영 후, 콘텐츠팀이 **실제로 어느 쪽 파일로 편집했는지**
- 성공: 쏙으로 받은 파일을 씀 · 실패: 결국 카톡 파일로 편집
- 왜 이렇게 재는가: 말로 물으면 다 "화질 중요하죠"라고 답한다. 어느 파일을 실제로 열었는지가 유일하게 정직한 답이다
- 실패 시: [RESEARCH 3장](./RESEARCH.md#3-차별화-전략)의 쐐기를 "전송이 안 끊긴다"로 교체

#### H5 · 골라 담기 — 받는 쪽은 전부가 아니라 일부만 필요하다

- 측정: 업로드된 전체 대비 실제로 골라 내려받은 비율
- 성공: 50% 미만만 내려받음(= 고르는 행위가 실재) · 실패: 대부분 전체 다운로드
- 실패 시 파장이 큼: 차별점이 "필요한 것만 골라 가기"가 아니라 "안 깨지고 안 끊기는 업로드"로 이동한다. 후자는 순수 인프라 싸움이라 훨씬 지키기 어려운 약속 → **서비스 한 문장 정의를 다시 써야 함**

#### H6 · 구글 드라이브로는 충분하지 않다 -> 가장 위험

- 측정: ① 현재 드라이브 사용 여부 ② 썼다가 관뒀다면 언제·왜 ③ 지난 행사 촬영본이 **지금 어디 있는지**
- 성공: 안 쓰거나 썼다가 이탈 · 실패: "드라이브에 잘 있어요"
- 왜 위험한가: 받은 피드백에 에어드롭·밴드·카톡은 나왔지만 **드라이브 언급이 한 마디도 없다.** 이 집단이 드라이브로 충분하다면 이 타겟은 통째로 무효
- **1호 케이스 착수 전에 먼저 확인할 것**

### 타겟 폐기 조건

아래 중 둘 이상 해당하면 이 타겟을 접고 [4장 C단계](#4-검증-단계)(러닝크루 등)로 이동한다.

- [ ] H6 실패 — 드라이브로 충분함이 확인됨
- [ ] H1 실패 — 강제력이 있는데도 업로드율 30% 미만
- [ ] H3가 3개 행사 연속 0건
- [ ] H5 실패 + H4 실패 (차별점이 둘 다 없음)

## 4. 검증 단계

**A단계 · 리허설 — 우테코 내부 (1주)**

- 목적: 제품 검증 아님. **링크가 안 깨지고 굴러가는지**만 확인
- 주의: 크루는 개발자이고 팀 지인이라 호의로 써준다. **여기서 나온 만족도는 신호로 쓰지 않는다**
- 산출: 운영 체크리스트, 깨지는 지점 목록

**B단계 · 실전 1호 — 홍보대사 팀**

컨시어지 MVP로 운영한다. 참여자에게는 쏙 화면만 보이고, 뒤는 손으로 처리해도 된다.

1. 취합 담당자에게 **쏙 브랜딩된 업로드 링크** 제공
2. 참여자는 설치·로그인 없이 링크 열고 바로 업로드
3. 모인 결과를 **골라 담을 수 있는 형태**로 콘텐츠팀에 전달
4. **기존 방식(카톡)과 병행** — H4를 재려면 비교군이 필요
5. 전 과정 기록 → H1 · H4 · H5 판정
6. (1차 조사 초안 기준) 실제 홍보대사 활동 과정에서 **1주일** 동안 사용을 요청하고, 사진을 공유하는 과정에서 어떤 기능을 실제로 쓰는지 확인한다

착수 전 확인 (미확인 시 B단계 시작 불가):

- [ ] **홍보대사 안에서 촬영본을 모으는 사람이 누구인가** — 피드백을 준 분은 "콘텐츠 팀 입장에서는"이라고 3인칭으로 말했다. 본인이 취합 담당이 아닐 수 있고, 그렇다면 그분은 **유저가 아니라 소개해주는 사람**이다. 진짜 첫 유저는 그 뒤에 있다
- [x] **다음 촬영 일정이 언제인가** — 이 날짜가 나와야 나머지 일정이 전부 정해진다. → **지금 가장 급한 액션** (8월 18일 ~ 8월 20일)
- [ ] H6 확인 — 드라이브 쓰는지, 지난 촬영본이 지금 어디 있는지
- [ ] 옆 학교 홍보대사 연결 가능한지

**C단계 · 확장**

- 2~3팀 추가 확보. 1호의 성패와 무관하게 진행한다 — **n=1 과의존을 막기 위한 장치**
- 열정적인 초기 유저는 웬만한 불편을 참아준다. "이 정도면 쓸 만하다"는 착각을 막으려면 비교군이 필요
- H2 · H3 판정은 이 단계에서
- 여기서 **버스킹·러닝크루·운동 소모임**을 2차 후보로 투입 가능

**순서를 이렇게 잡은 이유 (강제력의 함정)**

- 강제력 높은 집단(홍보대사·학생회) — 업무라서 업로드는 확실히 일어난다. 대신 조직이 모아준 것이지 제품이 모은 것이 아니다.
- 강제력 낮은 집단(버스킹 등) — 업로드가 일어나면 그건 진짜 신호. 대신 실패해도 **제품이 문제인지 그냥 아무도 안 올린 건지 안 갈린다.**

그래서 강제력 있는 집단에서 먼저 **"올리게만 하면 쓸모가 있나"**를 확인하고, 그다음 강제력 낮은 집단으로 **"안 시켜도 올리나"**를 확인한다. H3는 강제력 안에서도 자생적 획득이 일어나는지를 보는 장치다.

## 5. 측정 지표

| 지표                     | 정의                                    | 대응 가설 |
| ------------------------ | --------------------------------------- | --------- |
| 참여자 업로드율          | 링크 배포 인원 중 1장 이상 올린 비율    | H1        |
| 인당 업로드 수           | 참여자 1명당 평균 업로드 개수           | H1        |
| 선택 다운로드율          | 전체 업로드 대비 실제 내려받은 비율     | H5        |
| 재사용                   | 2회차 자발적 재요청 여부                | H2        |
| **참여자 → 생성자 전환** | 초대받았던 사람이 새 공유방을 만든 건수 | **H3**    |
| 편집 소재 출처           | 콘텐츠팀이 실제로 편집에 쓴 파일의 출처 | H4        |

**해석 원칙** — 업로드율 단독으로 판단하지 않는다. **업로드율이 높은데 H3가 0이면** 그건 제품이 아니라 조직 강제력이 만든 숫자다.

## 6. 가장 중요한 검증 질문

① 원본 화질과 필요한 사진만 선택해서 받을 수 있다는 점이 기존 방식보다 편리한가?
② 실제 사진 공유 상황에서 기존 방식 대신 이 서비스를 사용하는 행동이 나타나는가?
③ 일주일 동안 실제 활동에 사용했을 때에도 사진을 공유할 때마다 서비스를 다시 사용하는가?

단순히 "이런 기능이 있으면 좋겠다"는 요구를 확인하는 것을 넘어, 실제 사용 상황에서 사용자가 서비스를 선택하고 반복적으로 사용하는지까지 확인한다.
