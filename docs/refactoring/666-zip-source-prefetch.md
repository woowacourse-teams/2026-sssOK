# [ZIP 압축] 원본 미리 열기·부하테스트 기록

> #582 측정에서 발견한 "압축 시간이 사진 수에 정비례하고 CPU 는 놀고 있는 문제"의 개선 기록이다. 배경 측정은 `582-download-zip.md` 6·7절에 있다.
> 결과 문서에는 인증 토큰·서명 URL 원문을 남기지 않는다.

## 1. 작업 개요

- 담당: 현미밥(@gahyeonnni)
- 이슈 / PR: #666 / #862 (구현, squash 머지 `2ca823c6`). 이 기록은 별도 문서 PR 로 올린다.
- 상위 이슈: #556 / 발견: #582 (#662, #664) / 선행: #665 (압축 전용 실행기, #834)
- 대상 처리: `DownloadCompressionWorker` (압축 전용 실행기 `downloadCompressionTaskExecutor` 에서 실행)
- 개선 전 문제:
  - 동시 1개에서 30·100·300장 압축이 장당 약 0.11~0.12초씩 늘어난다. 상한 1000장이면 약 2분이다.
  - 그동안 호스트 CPU 는 약 10% 다. 계산보다 파일마다 기다리는 시간이 대부분이다.
  - 워커는 원본을 한 장씩 순서대로 스토리지에서 열어(`openDownloadStream`) zip 에 쓴다. 다음 파일의 GET 은 앞 파일을 다 쓴 뒤에야 시작한다.
  - 압축 한 건이 길수록 압축 워커를 오래 잡는다. 그래서 동시 압축 상한(#665)에 닿는 시점도 앞당겨진다.
- 유지해야 할 동작:
  - ZIP API 계약은 그대로다. 계약에는 압축 도중 진행률이 보이는 것, 원본 바이트 보존, 실패 시 업로드 abort, zip 항목 순서가 포함된다. `ZipDownloadApiTest` 가 보호한다.
  - 압축 중에는 DB 커넥션을 잡지 않고 상태 전이만 짧게 커밋한다.

## 2. 변경 내용

| 커밋 | 내용 |
| --- | --- |
| `feat(backend): ZIP 압축 구간별 시간 계측 추가` | `CompressionStageClock` 이 압축 한 건의 시간을 다섯 구간으로 나눈다: 원본 열기(open, GET 첫 바이트까지) · 본문 읽기(read) · 압축(deflate) · 업로드(upload) · 진행률 커밋(progress). 성공한 잡마다 `zip 압축 구간` INFO 로그와 지표 `sssok.download.compression.stage{stage}`·`sssok.download.compression.files` 를 남긴다 |
| `feat(backend): 원본 미리 열기 설정과 전용 실행기 추가` | 설정 `download.compression.prefetch-depth`(환경변수 `DOWNLOAD_COMPRESSION_PREFETCH_DEPTH`, 기본 3, 0 이면 끔)를 추가했다. 전용 실행기 `downloadSourcePrefetchTaskExecutor`(스레드 `media-worker-zip-prefetch-*`)는 크기가 워커 수 × depth 이고 대기열이 없다. 종료할 때 압축 풀 다음에 비운다 |
| `perf(backend): 압축 중 다음 원본 GET 을 겹쳐 열기` | `SourcePrefetcher` 가 현재 파일을 압축하는 동안 다음 원본 GET 을 최대 depth 개 미리 연다. 자세한 동작은 아래 목록에 있다 |
| `perf(backend): zip 압축 수준을 가장 빠른 단계로 조정` | `Deflater.BEST_SPEED`. 대상이 이미 압축된 사진이라 크기 이득은 작고 CPU 시간이 크다 |

`SourcePrefetcher` 의 동작:

- GET 을 시작하는 순서는 대상 순서를 지킨다. 그래서 zip 항목 순서, 진행률, 실패 사유가 기존과 같다.
- 앞 파일 열기가 실패하면 더 열지 않는다. 그 파일 차례에 원래 예외를 던진다.
- 압축이 끝나거나 실패하면 열어 둔 스트림을 닫아 커넥션을 돌려준다.
- 실행기가 가득 차 작업을 거절하면, 워커가 기존처럼 직접 연다.

- 진행률 커밋 빈도는 바꾸지 않았다. 측정해 보니 장당 2~6ms 로 작았다(아래 6절).
- 버전 의도: patch (API 계약 변화 없음)
- 압축 수준 근거(로컬 벤치): 기본 수준보다 약 40% 빠르고 zip 크기는 약 1.3% 커졌다. 수준 0(무압축)은 생성 PNG 기준으로 크기가 약 2배가 되어 제외했다.

## 3. 동작 보호

- 최신 develop 위로 리베이스한 뒤 관련 테스트 54건이 통과했다. 대상은 `CompressionStageClockTest`·`SourcePrefetcherTest`·`DownloadCompressionWorkerTest`·`TaskExecutorConfigTest`·`TaskExecutorDrainerTest`·`ZipDownloadApiTest` 다.
- PR CI 의 전체 테스트도 통과했다.
  - 첫 실행에서 `UploadTracingPostgresTest` 1건이 실패했다. ZIP 경로와 무관한 업로드 트레이싱 테스트다.
  - 로컬에서 이 테스트만 3회 돌려 모두 통과해, 간헐 실패로 보고 실패한 잡만 재실행했다. 재실행은 통과했다.
- `ZipDownloadApiTest` 의 진행률 계약 테스트는 "두 번째로 여는 원본에서 멈춘다"를 전제로 한다. GET 시작 순서를 대상 순서로 지키는 설계라 테스트를 고치지 않고 통과했다. 이 테스트만 10회 반복해도 모두 통과했다.
- 추가한 테스트:
  - `SourcePrefetcherTest`
    - 순서대로 depth 개만 미리 연다.
    - 앞 파일 열기가 실패하면 원래 예외를 던지고 더 열지 않는다.
    - close 하면 열어 둔 스트림을 닫는다.
    - 실행기가 거절하면 워커 스레드에서 직접 연다.
    - GET 대기를 depth 개까지 겹친다(동시 최대 3개, 전체 400ms 미만).
    - depth 0 이면 실행기를 쓰지 않는다.
  - `CompressionStageClockTest`: 구간별 시간 분리, 그리고 압축 = 쓰기 − 읽기 − 업로드 계산
  - `DownloadCompressionWorkerTest`: 성공하면 구간 지표 다섯 개와 파일 수를 기록하는지 확인
  - `TaskExecutorConfigTest`: 미리 열기 풀 크기 = 워커 수 × depth

## 4. 로컬 동작 확인

로컬 서버를 일회용 Postgres 와 MinIO 에 붙여 띄웠다. MinIO 앞에는 GET 마다 60ms 를 지연시키는 프록시를 두어 원격 스토리지의 첫 바이트 대기를 흉내 냈다. AI 는 끄고 디스코드 웹훅은 비웠다.

| 확인 항목 | 결과 |
| --- | --- |
| 개선 전 (develop) | 장당 약 90ms |
| 미리 열기 끔 (depth 0) | 장당 약 88ms 중 open 약 69ms(약 78%), 압축 약 6ms, 업로드 약 5ms, 커밋 약 1~1.5ms |
| 미리 열기 depth 3 | 장당 32~39ms. 300장이 약 27초에서 9.6초로 줄었다 |

로컬 수치는 방향을 확인하는 용도다. 공식 전후 비교는 아래 dev 측정으로 한다. 확인을 마친 뒤 서버와 프록시를 내렸고, 일회용 DB 와 이번에 만든 MinIO 객체만 지웠다.

### 해석

- **장당 시간이 절반 가까이 줄었다.**
  - 300장 압축이 32.5초에서 16.0초로 줄었다(장당 108ms → 53ms).
  - 사진이 많을수록 효과가 크다. 30장은 −24%, 100장은 −46%, 300장은 −51% 다.
  - 30장처럼 짧은 압축은 마지막 업로드(close)처럼 사진 수와 무관한 몫이 커서 줄어든 비율이 작다.
- **줄어든 것은 원본 열기다.**
  - 미리 열기를 끄면 장당 시간의 약 60%(76~78ms)가 GET 첫 바이트 대기였다.
  - 미리 열기를 켜면 17~19ms 로 약 4분의 1 이 됐다.
  - 진행률 커밋은 장당 2~6ms, 압축은 8~9ms 라 처음부터 주된 비용이 아니었다. 진행률 커밋 빈도는 그래서 그대로 뒀다.
- **처리량이 늘었다.**
  - 4분 처리 수가 동시 4 에서 221 → 335(+52%), 동시 8 에서 412 → 571(+39%), 동시 12 에서 452 → 714(+58%)다.
  - 압축 한 건이 짧아져 같은 워커 8개로 더 많이 처리한다.
  - 동시 12 의 서버 대기도 1.60s 에서 0.82s 로 줄었다. 워커를 넘는 4건이 기다리는 구조는 그대로다.
- **늘어난 처리량만큼 CPU 를 더 쓴다.**
  - 동시 12 에서 호스트 CPU 평균이 60% 에서 78% 로, 최대가 86% 로 올랐다. 프로세스 CPU 는 100% 에 닿은 순간이 있었다.
  - 이 구간에서는 deflate 가 장당 8ms 에서 18ms 로 늘어 CPU 경합이 시작됐다.
  - 동시 1 의 CPU 는 10% 에서 11~15% 로 거의 그대로다.
- **메모리와 커넥션은 여유가 있다.**
  - 힙 최대는 before 와 같은 범위였다(최대 424MB, 상한 512MB).
  - 미리 열어 둔 스트림은 본문을 읽기 전이라 버퍼를 거의 쓰지 않는다.
  - 동시 GET 은 압축 1건당 최대 3개다. 미리 열기 실행 최대 14 에 현재 파일 GET 을 더해도 SDK 기본 커넥션 상한(50) 안에 들어온다.
- **다음 병목은 업로드다.**
  - after 에서는 장당 23~59ms 로 가장 큰 구간이다.
  - zip 을 R2 에 8MB 파트 단위로 동기 업로드해, 파트를 올리는 동안 압축이 멈춘다.
  - 30장에서만 장당 업로드가 32ms 에서 59ms 로 커졌지만, 한 건 기준 100·300장은 같거나 줄었다. 업로드가 느려졌다고 보지 않고 편차로 남긴다.
  - 미리 연 GET 이 같은 시간대에 네트워크를 나눠 쓸 가능성은 있다. 이를 확인하려면 30장 단계를 depth 0·3 으로 번갈아 여러 번 재야 해서 이번 범위에서는 하지 않았다.
