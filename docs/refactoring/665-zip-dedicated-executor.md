# [ZIP 압축] 전용 실행기 분리·부하테스트 기록

> #582 측정에서 발견한 "압축이 공용 워커 풀에서 동시 4개로 묶이는 문제"의 개선 기록. 배경 측정은 `582-download-zip.md` 6·7절을 본다.
> 결과 문서에는 인증 토큰·서명 URL 원문을 남기지 않는다.

## 1. 작업 개요

- 담당: 현미밥(@gahyeonnni)
- 이슈 / PR: #665 / #834 (구현, 머지 `93460c60`) · 이 기록은 별도 문서 PR
- 상위 이슈: #556 / 발견: #582 (#662, #664)
- 대상 API·후속 처리:
  - `POST /api/v1/rooms/{roomId}/downloads/zip`: ZIP 요청. 202 응답과 함께 QUEUED 잡을 만든다.
  - `GET /api/v1/rooms/{roomId}/downloads/zip/{jobId}`: ZIP 상태 조회.
  - 후속 처리: `DownloadJobRequestedEvent` → `AFTER_COMMIT` → 압축 워커
- 개선 전 문제:
  - 압축이 공용 풀 `applicationTaskExecutor`(`spring.task.execution` core 4 · max 8 · queue 100)에서 돈다.
  - `ThreadPoolTaskExecutor` 는 큐(100)가 찰 때까지 core 를 넘겨 스레드를 늘리지 않는다. 그래서 max 8 이 쓰이지 않고 동시 압축이 4개로 묶인다.
  - 동시 5부터 대기가 생기고 처리량은 분당 약 60건에서 멈춘다. 그동안 호스트 CPU 는 50% 아래이고 DB 커넥션 대기도 0 이다.
  - 같은 풀을 스토리지 정리·알림이 함께 써서, 압축이 몰리면 그 작업들도 같은 큐에서 기다린다.
  - 풀이 가득 차 제출이 거부되면 잡이 QUEUED 로 남아 stale 정리(30분)까지 사용자의 동시 잡 한도(3)를 차지한다(#582 7절 후보).
- 유지해야 할 동작:
  - ZIP API 계약(요청·응답 형식, 400·404·429 판정, 상태 전이, 다운로드 URL)은 그대로다. `ZipDownloadApiTest` 가 보호한다.
  - 압축 중에는 DB 커넥션을 잡지 않고 상태 전이만 짧게 커밋한다.

  - `TaskExecutorConfigTest`: 압축 풀이 core = max 로 설정 값만큼 바로 동시에 돌고, 기본값·범위 검증이 맞는지 확인한다.
  - `DownloadJobTest`: QUEUED → FAILED 전이.

### 해석

- **동시 4 상한이 풀렸다.** after 는 실행 스레드가 동시 수만큼(최대 8) 바로 늘었다. before 는 동시 4 이후 실행이 4 에 묶였다.
- **동시 5·8 에서 대기가 사라졌다.** 서버 대기가 동시 5 에서 0.59s → 0.05s, 동시 8 에서 3.42s → 0.06s 로 줄었다. 사용자 체감인 k6 완료 p95 는 동시 8 에서 9.2s → 5.2s 다.
- **처리량이 늘었다.** 4분 처리 수가 동시 8 에서 247 → 408(+65%), 동시 12 에서 253 → 446(+76%)이다. 분당으로는 약 62건 → 102·112건이다.
- **동시 12 는 워커 수(8)를 넘는 만큼 기다린다.** 큐 최대 4(= 12 − 8), 서버 대기 1.64s 로, before(큐 8, 7.30s)보다 짧다. 설정대로 동작한다.
- **동시 1·2·4 는 같은 수준이다.** 워커 수가 상한에 닿지 않는 구간이라 바뀔 이유가 없다. 동시 2 의 처리 수가 112 → 94 로 준 것은 그 단계의 압축 시간이 3.8s → 4.6s 로 길어진 탓인데, CPU·대기는 같고 단계별 1회 측정이라 그 시각 R2 응답 차이로 본다(#582 에서도 같은 조건의 압축 시간이 측정 시각에 따라 약 10% 달랐다).
- **늘어난 처리량만큼 CPU 를 쓴다.** 동시 8·12 에서 CPU 평균이 35~37% → 53~61%, 최대 78% 까지 올랐다. 압축 한 건의 시간도 동시 12 에서 3.9s → 4.4s 로 약 10% 늘어, 2 vCPU 에서 CPU 경합이 시작되는 지점에 가깝다.
- **힙은 걱정했던 만큼 늘지 않았다.** 실행 8 에서도 힙 최대 407~434MB(상한 512MB)로 before(실행 4, 433~458MB)와 같은 수준이었다. 힙 최대치는 GC 시점에 따라 흔들려 실행 수에 정비례하지 않는다. 압축 하나당 업로드 버퍼(8MB) × 8 = 64MB 는 이 범위 안에 들어온다.
