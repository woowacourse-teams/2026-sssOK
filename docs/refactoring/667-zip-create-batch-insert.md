# [ZIP 접수] 대상 저장 묶음 insert·부하테스트 기록

> #582 측정에서 발견한 "접수 API 처리 시간이 압축 대상 수에 비례해 늘어나는 문제"의 개선 기록이다. 배경 측정은 `582-download-zip.md` 6·7절에 있다.
> 결과 문서에는 인증 토큰·서명 URL 원문을 남기지 않는다.

## 1. 작업 개요

- 담당: 현미밥(@gahyeonnni)
- 이슈 / PR: #667 / #866 (구현, squash 머지 `1775e198`). 이 기록은 별도 문서 PR 로 올린다.
- 상위 이슈: #556 / 발견: #582 (#662, #664)
- 대상 처리: `CreateDownloadJobService.create` → `DownloadJobRepository.saveJobMedia`
- 개선 전 문제:
  - 동시 1개에서 접수 서버 평균이 30·100·300장에 53·115·314ms 로, 대상 1장당 약 1ms 씩 늘었다(#582 new). 상한 1000장이면 1초 안팎으로 예상됐다.
  - 접수는 요청자 행을 잠근 트랜잭션 하나에서 진행 중 잡 수를 세고, 잡과 대상(`download_job_media`)을 저장한다. 트랜잭션이 길수록 같은 요청자의 다음 요청과 계정 병합 등이 잠금을 기다린다.
- 유지해야 할 동작:
  - 요청자당 동시 진행 한도(429) 판단과 잡·대상 저장이 같은 트랜잭션이어야 한다. 잡만 있고 대상이 없는 상태가 생기면 안 된다.
  - ZIP API 계약(대상 고정, `mediaCount`, 400·404·429)은 그대로다. `DownloadControllerTest` 가 보호한다.

## 2. 개선 전 시간 구성

먼저 300장·1000장 접수의 시간을 구간별로 나눠 쟀다. 측정 환경은 로컬 Testcontainers Postgres 이고, 서비스 메서드 구간을 7회 재서 중앙값을 냈다. 이 계측 코드는 커밋하지 않았다.

| 구간 | 300장 | 1000장 |
| --- | --- | --- |
| 대상 해석 (`DownloadTargetResolver.resolve`) | 3.9ms | 13.6ms |
| 요청자 잠금 + 진행 중 잡 수 조회 | 2.2ms | 2.0ms |
| 잡 저장 | 0.5ms | 0.4ms |
| **대상 저장 (`saveJobMedia`)** | **50.5ms** | **171.3ms** |
| 서비스 전체 (커밋 포함) | 62.3ms | 190.6ms |

- 대상 저장이 접수 시간의 80~90% 를 차지했다.
  - `download_job_media` 의 키가 IDENTITY 라 JPA `saveAll` 이 행마다 insert 를 따로 보낸다.
  - Hibernate 는 IDENTITY 키의 insert 를 배치로 묶지 않는다. 저장할 때마다 생성된 키를 바로 받아야 하기 때문이다.
- 대상 해석은 이미 잠금보다 먼저 한다. 잠금 범위와 해석 순서는 바꿀 것이 없었다.

## 3. 변경 내용

| 커밋 | 내용 |
| --- | --- |
| `perf(backend): ZIP 접수 대상 저장을 JDBC 배치 insert 로 변경` | `saveJobMedia` 를 `JdbcTemplate.batchUpdate` 한 번으로 바꿨다. JPA 를 거치지 않으므로 엔티티가 채우던 `created_at`·`updated_at` 은 UTC 시각으로 직접 넣는다. 같은 트랜잭션의 연결을 쓰므로 접수가 롤백되면 대상 행도 함께 사라진다 |

- 읽기(`findMediaIdsByJobId`)와 스키마 검증 때문에 `DownloadJobMediaJpaEntity` 는 그대로 뒀다.
- 버전 의도: patch (API 계약 변화 없음)

### 고르지 않은 방법

| 방법 | 고르지 않은 이유 |
| --- | --- |
| Hibernate 배치 설정(`hibernate.jdbc.batch_size`) | IDENTITY 키에서는 insert 배치가 꺼져 효과가 없다 |
| ID 전략을 SEQUENCE 로 변경 | Hibernate 배치가 동작하지만, 마이그레이션으로 시퀀스 증가폭을 `allocationSize` 에 맞추고 엔티티도 바꿔야 한다. 테이블 하나의 저장 속도 때문에 키 생성 방식을 바꾸기엔 범위가 크다 |
| Postgres 전용 한 문장 insert(`unnest(배열)`, VALUES 여러 줄) | 문장이 하나라 이론상 더 빠르지만 Postgres 문법에 묶이고 SQL 을 동적으로 만들어야 한다. 배치로 이미 300장 3.4ms 라 얻을 것이 적다고 봤다(따로 측정하지 않았다) |
| pgjdbc `reWriteBatchedInserts=true` | dev·prod `DB_URL` 이 저장소 밖 서버 환경변수로 관리되고, 앱 전체 배치에 영향을 준다. 더 줄여야 하면 다음 후보다 |
| 대상 ID 를 잡 테이블에 배열·JSON 컬럼으로 저장 | 행 수는 1개로 줄지만 스키마와 워커 읽기 코드가 바뀌어 이슈 범위를 넘는다 |
| 대상 저장을 잠금 트랜잭션 밖으로 빼기(비동기 등) | 잠금 시간은 가장 크게 줄지만 1절의 계약을 깬다 |

## 4. 동작 보호

- ZIP 관련 테스트 20개 클래스가 통과했다.
  - `DownloadControllerTest` 24건(대상 고정·`mediaCount`·400·404·429 계약)은 고치지 않았다.

- 추가한 테스트: `DownloadJobRepositoryTest` (Postgres)
  - 상한 1000건을 한 번에 저장한다.
  - 생성·수정 시각이 저장 시점으로 남는다.
  - 잡 사이에 대상이 섞이지 않는다.
  - 접수 트랜잭션이 롤백되면 잡과 대상이 함께 사라진다. JDBC 배치가 별도 연결로 바로 커밋되면 이 테스트가 실패한다.

### 해석

- **접수 시간이 더 이상 대상 수에 비례하지 않는다.**
  - before 는 30장에서 300장으로 갈 때 64ms → 358ms 로, 대상 1장당 약 1.1ms 씩 늘었다.
  - after 는 31ms → 48ms 로, 270장이 늘어도 17ms 만 늘었다. 장당 약 0.06ms 다.
  - 300장 기준 접수 서버 평균이 358ms 에서 48ms 로 약 7분의 1 이 됐다.
- **줄어든 것은 대상 저장이다.** 2절에서 대상 저장이 접수 시간의 80~90% 였고, 로컬 계측에서 이 구간이 300장 약 15분의 1, 1000장 약 13분의 1 로 줄었다. dev 에서도 같은 모양으로 줄었다.
- **잠금을 잡는 시간도 그만큼 줄었다.** 대상 저장은 요청자 행을 잠근 뒤에 일어나므로, 같은 요청자의 다음 접수나 계정 병합이 기다리는 시간도 함께 줄어든다. 잠금 대기 자체는 이번에 따로 재지 않았다.
- **늘어난 처리 수는 접수가 짧아진 만큼이다.** 시나리오가 접수 → 압축 완료를 반복하므로 접수가 짧아지면 같은 4분에 반복이 늘어난다. 압축 경로는 바꾸지 않았다.
- **CPU·DB 는 같은 수준이다.** 호스트 CPU 는 15~20% 로 비슷했고, DB 커넥션 대기는 두 측정 모두 0 이었다.
- **남은 비례 몫은 대상 해석이다.** 로컬 계측 기준 1000장에서 약 14ms 다. 상한 1000장에서도 접수가 100ms 안팎에 머물 것으로 보이지만, dev 에서 1000장은 재지 않았다.
