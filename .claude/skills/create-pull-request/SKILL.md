# PR 생성

PR을 만들기 전에 저장소 루트의 `AGENTS.md` 를 읽고 "PR" 섹션 규칙을 따른다.
(세부 배경이 필요하면 `docs/collaboration/PR_GUIDE.md` 도 함께 읽는다.)

이 스킬은 **일반 작업 브랜치 → `develop`** PR 전용이다 (`hotfix/*` 는 `main` 대상).
`develop` 에 쌓인 걸 운영으로 승격하는 `develop → main` PR은 `promote-to-main` 스킬을 쓴다 —
승인 조건과 머지 방식(merge commit)이 다르다.

## 작업 절차

1. 현재 브랜치와 연결된 이슈 번호를 확인한다. 브랜치명에서 `#숫자` 를 읽으면 된다.
2. 대상 브랜치를 정한다 — 브랜치명이 `hotfix/*` 면 `main`, 그 외엔 `develop`.
3. 대상 브랜치를 최신으로 받아 현재 브랜치와의 diff 를 확인한다.
   대상 브랜치보다 뒤처져 있으면 먼저 동기화하도록 안내한다.
5. diff 규모를 확인한다. 500줄을 크게 넘으면 쪼갤 수 있는지 사용자와 상의한다.
6. `.github/pull_request_template.md` 구조에 맞춰 본문을 채운다.
   - 작업 내용: 무엇을 왜 했는지
   - 관련 이슈: `Closes #번호`
   - 작업 영역: 실제 바뀐 경로에 맞게 체크
   - 변경 사항: 커밋 단위로 요약
   - 테스트: 실제로 실행한 것만 체크한다. 안 돌렸으면 체크하지 않는다
   - 리뷰 요청 사항: 판단이 갈리는 지점, 컨벤션과 다르게 간 부분, 미해결 항목
7. 커밋되지 않았거나 푸시되지 않은 변경이 있으면 먼저 알린다.
8. **제목과 본문 전문을 사용자에게 보여주고 확인을 받는다.**
9. 승인되면 푸시하고 `gh pr create` 로 만든 뒤, PR 번호와 링크를 알려준다.

## 주의 사항

- **이 스킬은 PR을 병합하지 않는다.** 셀프 머지는 팀 규칙 위반이다.
- **완료 조건이 남았으면 `Closes #` 를 넣을지 사용자에게 확인한다.** 넣으면 머지 시 이슈가 자동으로 닫힌다.
- 리뷰어를 직접 지정하지 않는다. CODEOWNERS 가 자동으로 지정한다.
- 다른 사람의 파일을 수정했다면 본문에 명시한다. 리뷰어가 놓치기 쉽다.
- 테스트 체크박스를 실제 실행 없이 채우지 않는다. 결과를 그대로 적는다.
